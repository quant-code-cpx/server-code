## 3. 业务理解与不变量

### 3.1 三类预算必须分离

| 编号 | 业务规则 | 来源 | 测试影响 |
| --- | --- | --- | --- |
| R-001 | 单次模型输入与预留输出之和不得超过该次实际候选模型的 `contextWindow` | 模型部署能力 | 每次 attempt 调用前校验；不能由 Run 静态常量覆盖 |
| R-002 | 单次请求 `maxOutputTokens` 不得超过该候选模型的 `maxOutputTokens` | 模型部署能力 | MANUAL/AUTO/fallback 都以 Run 创建快照为准 |
| R-003 | Run 累计输入/输出/金额/调用数是显式执行或成本策略，不是模型能力 | 用户需求 | 字段、错误、事件和 UI 必须使用“Run 护栏/成本预算”语义 |
| R-004 | Run 创建时冻结模型候选能力与成本策略；处理中途配置漂移不改变既有 Run | 可审计与可复现 | Checkpoint/恢复、重试、fallback 使用同一快照 |
| R-005 | AUTO 按所有允许 fallback 候选的保守能力预构建上下文；MANUAL 不静默换模型 | 路由契约 | 小窗口 fallback 前不出现供应商 context-length 错误 |
| R-006 | 调用前以保守估算决策；调用后以真实 usage 记账 | 用户需求 | 估算不是账单；真实 usage 不得反转已成功模型调用 |
| R-007 | 成功调用导致 Run 护栏超额时，保留成功结果并记录超额/阻止后续调用；不得伪造本次调用失败 | 用户需求 | 终态、事件、审计必须一致 |
| R-008 | 无真实 usage 时记录保守估算并标记来源；不得冒充供应商精确值 | 模型网关契约 | SSE、审计、汇总保留 `actual/estimated` 语义 |

### 3.2 上下文与安全不变量

| 编号 | 业务规则 | 测试影响 |
| --- | --- | --- |
| R-009 | 当前问题、必要系统约束、工作流约束、已完成工具事实不可静默丢失 | 超限应调用前压缩或明确停止 |
| R-010 | 优先确定性裁剪工具目录、过大工具结果、旧历史；摘要只处理选定旧片段，不每轮重喂全部上下文 | 验证 segment manifest 与 Token 变化 |
| R-011 | 摘要结构化、版本化、可校验，保留来源消息/工具事实/引用/时间范围；原文不删除 | 摘要失败、过期、CAS 冲突与引用丢失均安全回退 |
| R-012 | 外部网页/工具内容是不可信数据，不能覆盖系统/工作流指令 | Prompt injection 场景不能提升权限或改变工具策略 |
| R-013 | Token 计量须支持真实 tokenizer、供应商 count 能力或实测校准的保守估算；中文/JSON/工具 schema 不得使用统一字符数除四 | 校准语料必须覆盖中英文、JSON、schema、Unicode |
| R-014 | 502、429、超时、连接中断与本地预算/结构化校验错误分开分类 | 重试/fallback/错误 UI 不混淆根因 |
| R-015 | 事件、审计、Checkpoint、REST 与 UI 对预算和 usage 的字段、来源、单位一致 | 合同生成与前端 reducer 必须回归 |

## 4. 风险清单

| 风险 | 业务影响 | 测试策略 | 优先级 |
| --- | --- | --- | --- |
| 静态 32K 覆盖 128K 模型能力 | 长链在成功后被错误标记 6018 | 128K 配置 + 累计输入越过 32K 回归 | P0 |
| 估算偏低，尤其中文/JSON/schema | 供应商拒绝或事后超额 | 校准语料、上界/误差带、调用前 headroom | P0 |
| 估算偏高 | 过早压缩、成本和延迟增加 | 对比 tokenizer/真实 usage，记录误差率 | P1 |
| 成功调用被事后改失败 | 用户丢失已生成结果、审计失真 | usage 超额成功模型固定为成功，Run 只阻止下一调用 | P0 |
| fallback 小窗口未纳入预算 | 切换后 context-length 失败 | AUTO 最小候选、重试后切换验证 | P0 |
| 配置在 Run 中途改变 | 同一 Run 不可复现 | Run 快照和 checkpoint 恢复验证 | P0 |
| 摘要丢事实/引用/时间范围 | 研究结论不可追溯 | 结构校验、来源 ID、引用覆盖、失效回退 | P0 |
| 工具目录固定占用过大 | 上下文耗尽 | 按意图选择、描述压缩与 hash/版本审计 | P1 |
| 外部内容提示注入 | 越权或污染结论 | 不可信区隔、恶意文本 E2E | P0 |
| 502/429 被误报预算错误 | 错误修复方向错误 | 故障分类、有限重试、Provider 证据 | P1 |
| SSE usage 丢失/重复 | UI/账单不一致 | usage 早到/晚到/重复幂等测试 | P1 |
| 队列重试重复记账 | 成本和配额失真 | attempt/modelCallId 幂等与恢复测试 | P0 |

## 6. 真实浏览器文案矩阵（冻结版）

### 会话 S01：个股行情与连续追问（贵州茅台）

1. `S01-M01`：贵州茅台最近一个交易日收盘表现怎么样？先给我一个简洁概览。
2. `S01-M02`：把最近一个月的走势和成交量变化一起看，哪些天比较异常？
3. `S01-M03`：如果把时间拉到半年，当前价格大致处在什么位置？
4. `S01-M04`：这半年最大回撤是多少，发生在哪段时间？
5. `S01-M05`：上涨日和下跌日的成交量有没有明显差别？
6. `S01-M06`：结合刚才的数据，区分短期波动和中期趋势。
7. `S01-M07`：有哪些结论是数据直接支持的，哪些只是推断？
8. `S01-M08`：如果我只关心未来一周，最值得观察的三个价量条件是什么？
9. `S01-M09`：再核对一次数据日期，避免把旧数据当成今天。
10. `S01-M10`：把整个分析压缩成一段风险中性的收尾，不要给买卖指令。

### 会话 S02：技术信号（宁德时代）

1. `S02-M01`：宁德时代最近的技术面处于偏强、震荡还是偏弱？
2. `S02-M02`：看一下均线结构，短中长期是否一致？
3. `S02-M03`：MACD 和 RSI 给出的信号有没有冲突？
4. `S02-M04`：最近一次明显的放量突破或放量下跌是什么时候？
5. `S02-M05`：布林带位置能说明当前波动状态吗？
6. `S02-M06`：如果出现假突破，数据上通常会先看到哪些迹象？
7. `S02-M07`：把这些指标按领先、同步、滞后分类。
8. `S02-M08`：不要重复定义，直接说当前最关键的两个确认条件。
9. `S02-M09`：如果部分指标缺数据，请明确指出，不要补造。
10. `S02-M10`：最后给我一个包含反例条件的技术面总结。

### 会话 S03：财务分析（美的集团）

1. `S03-M01`：美的集团最近一期财务质量怎么样？先看收入、利润和现金流。

4. `S03-M04`：ROE 的变化更可能来自盈利能力、周转还是杠杆？
5. `S03-M05`：资产负债表上最需要警惕的项目是什么？
6. `S03-M06`：应收、存货与收入增速是否协调？
7. `S03-M07`：把最新一期和上年同期做可追溯比较。
8. `S03-M08`：哪些财务字段在当前数据里缺失或可能滞后？
9. `S03-M09`：剔除一次性因素后，结论会不会变化？如果无法判断就直说。
10. `S03-M10`：用“优势、风险、待验证”三部分收尾。

### 会话 S04：个股与市场资金流（东方财富）

6. `S04-M06`：和券商板块整体资金表现相比，它偏强还是偏弱？
7. `S04-M07`：北向或市场级资金数据如果不可得，请分开说明。
8. `S04-M08`：资金流数据能支持趋势判断到什么程度？

### 会话 S06：指数与基金

1. `S06-M01`：沪深300最近三个月的走势和波动情况如何？
2. `S06-M02`：和中证500相比，大小盘风格谁更占优？

4. `S06-M04`：找一只跟踪沪深300的场内基金，说明近期跟踪表现。
5. `S06-M05`：基金净值、价格和指数日期能对齐吗？

## 7. 前端预算语义与可观测性用例矩阵

业务理解：Agent 页面解决长链量化研究的提问、工具取证和实时进度诊断；用户最依赖自然语言连续追问、结果证据、故障可解释性。数据流为浏览器 `POST` 创建/发送消息，SSE 事件进入 reducer，再由活动面板展示。边界包含无护栏、显式护栏、Provider 精确计数不可用、真实 usage 超过预估、fallback、断流和长文本。

## 8. 浏览器逐条记录字段

每条消息写入执行报告：`会话ID、消息ID、自然语言原文、conversationId、runId、模型策略、实际 Provider/模型、开始/结束时间、耗时、实际/估算 input/output/cached/reasoning token、成本、工具链、fallback/retry、错误分类、最终状态、关键结论、证据截图/事件序列`。

## 9. 执行顺序与停止条件

1. 先让关键单元/集成回归变红，确认能复现 32K 覆盖、估算偏差与事后假失败。
2. 修复后运行目标测试、Agent 相关测试、合同生成、前端 reducer/UI 测试和构建。
3. 启动真实 API、Agent Worker、Redis/PostgreSQL 与前端，检查迁移和日志。
4. 按 S01→S10 从真实 UI 连续发送；遇本地 Bug 立即修复并重测受影响链。
5. Provider 429/502/超时单列外部故障；仅按有界策略重试，不伪装成功。
6. 停止条件：可能污染数据、持续错误率过高、Provider 明确限流、成本护栏触发或安全边界异常；记录证据后修复/等待恢复。

## 10. 完成标准

- 三层预算在代码、配置、快照、审计、SSE、REST 与 UI 语义一致。
- 关键回归用例通过；真实 Token 与估算误差有可解释证据。
- 10 个独立会话、每个至少 10 条真实 UI 消息完成并逐条留档。
- 所有本地缺陷已修或有明确阻塞；外部 Provider 问题与本地问题分开。
- 编译、静态检查、单元、集成、业务场景、真实浏览器代表性回归均有命令与结果。
