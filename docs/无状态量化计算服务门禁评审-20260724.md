# 无状态量化计算服务门禁评审（2026-07-24）

## 1. 结论

Batch 024 本轮结论为 **no-go**：继续使用现有 TypeScript 确定性量化计算，不创建 Python Compute Service。

现有生产 Tool `compute_performance_metrics` 最多接受 10,000 点；代表性纯计算在该上限下耗时为 11.57–19.85 ms，未达到 [ADR-003](agent/decisions/adr-003-typescript-python-boundary.md) 的 30 秒拆分门禁。当前能力也不依赖 scipy、cvxpy 或 sklearn。

100 万点压力样本的 max RSS 达到 606.51–693.38 MiB，说明未来若真实 workload 扩展到百万点，应重新评估独立进程或 Python 服务；但该规模是当前 Tool 上限的 100 倍，不能据此为不存在的生产请求引入长期双语言成本。

## 2. 门禁与范围

本次复审使用 ADR-003 的四项启动条件：

1. 单任务 CPU 超过 30 秒；
2. 真实任务数据点超过 100 万；
3. Node 内存成为实际 workload 的瓶颈；
4. 明确需要 scipy、cvxpy 或 sklearn。

选取两个已版本化、无数据库依赖的真实实现：

- `performance-metrics-v1`：收益、波动、Sharpe、Sortino、回撤、VaR/CVaR；
- `valuation-percentile-v1`：排序、P1/P99 缩尾、分位数和样本过滤。

环境：Apple M2 Pro、macOS arm64、Node.js v24.5.0。输入使用确定性日期和值序列；fixture 构造耗时与纯计算耗时分开记录。每个规模使用独立 Node 进程，记录 wall time、CPU、heap 增量和进程 max RSS。

## 4. 门禁判定

| 门禁 | 证据 | 判定 |
| --- | --- | --- |
| CPU > 30 秒 | 最慢 100 万点为 1.34 秒；生产上限 10,000 点为 19.85 ms | 未达到 |
| 真实数据 > 100 万点 | 当前 Tool `maxItems=10,000`，无已批准百万点请求 | 未达到 |
| Node 内存瓶颈 | 生产上限 heap 增量 5.55–7.18 MiB；百万点压力样本内存显著，但不在允许路径 | 当前未达到 |
| 科学计算库依赖 | 当前算法只需排序、统计与确定性纯函数 | 未达到 |

## 5. 决策与重启条件

- 不创建 `services/quant-compute/`、Python Dockerfile、Nest client、mTLS/token 或第二套运行链。
- 不接入同级 `../data-service`；其数据库、认证、审计和运行边界仍不符合生产要求。
- TypeScript 实现继续是唯一权威版本；保持 Tool 输入上限与 BullMQ 长任务隔离。
- 出现以下任一真实证据时重新打开 Batch 024：
  - 已批准任务持续超过 100 万点；
  - 单任务 CPU 接近或超过 30 秒；
  - worker 内存/GC/事件循环 SLO 因量化计算持续失守；
  - 产品能力明确要求 scipy、cvxpy、sklearn 或同等级科学计算库。

重新打开后仍须先做同 fixture 的 TS/Python golden diff、输入/输出 hash、故障回退和无主库/无公网安全验证。
