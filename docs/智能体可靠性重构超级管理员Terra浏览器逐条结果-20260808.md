## 4. 认证专项证据

首要根因是 React StrictMode 首屏副作用重复触发会话恢复，加上此前自动化频繁整页刷新，短时间内重复调用 `/api/auth/refresh` 并触发限流。继续取证又发现二级根因：多个本地标签共享 HttpOnly Refresh Cookie，但一个陈旧标签刷新失败时会主动 logout 并广播登出；服务端 Refresh Token 的“检查→标记已用”也不是原子操作。

修复后：

- AuthProvider 对一次启动恢复使用单飞 Promise，StrictMode 重放不再产生第二次刷新。
- 启动恢复成功会向同源标签广播 Token；失败会等待 250ms 接纳并发标签的成功结果。
- 自动刷新失败只清除当前标签的内存身份，不再调用 logout 或广播全局登出；明确点击退出仍会撤销共享会话。
- 服务端通过 Redis Lua 原子消费 Refresh Token；并发请求只有一个进入轮换，其余进入 grace。
- 登录页初始验证码请求也做幂等保护。
- 本轮不再整页刷新切会话，使用站内 SPA 选择。
- 2026-08-08 11:35:26 access token 真实过期后，只出现一次 `POST /api/auth/refresh 201`；页面保持超级管理员登录并继续发送，没有新的 429。
- 补丁热重载后，12:09:25 多个本地页面同秒发出 5 个刷新请求，全部 201，没有 invalid/429；12:09:30 超级管理员 `userId=1` 继续读取 Agent 会话并返回 200；隔离 Redis 实测返回顺序为 `valid`、`grace`。
