## 一、目标与结论

### 1.1 目标

在保留现有条件订阅 CRUD、状态机、日/周/月调度和 WebSocket 通知的基础上，把“只执行股票筛选 filters”升级为可版本化的规则评估平台，支持：

1. `STOCK_SCREENING`：基础选股集合变化。
2. `FACTOR_SCREENING`：内置/自定义因子筛选集合变化。
3. `SIGNAL_EVENT`：MACD/KDJ/RSI/BOLL/MA/SAR/VOLUME 等技术事件。
4. `COMPOSITE`：P3 开放的多子规则组合，首期仅 AND。

扩展的前提是先解决现有执行正确性：500 条分页截断、交易日未注入底层查询、首次执行通知噪音、周/月技术事件漏报、缺乏命中证据和幂等通知。

### 1.2 推荐分期

| 阶段 | 内容 | 阻塞关系 |
| --- | --- | --- |
| B0 正确性基线 | 无分页 `screenCodes`、交易日锁定、首次执行基线、结构化错误、幂等 job | 所有阶段前置 |
| B1 规则内核 | `ruleSpec/triggerSpec`、Metric Catalog、validator、dispatcher、preview | 前端 v3 基础选股前置 |
| B2 因子评估器 | 因子全量集合、快照就绪检查、证据生成 | 因子订阅前置 |
| B3 技术事件 | 统一指标语义、全市场日级快照/事件、事件评估器 | 技术信号订阅前置 |
| B4 运行证据 | hit 表、run status、通知重试、详情 API | 完整运行台前置 |
| B5 复合规则 | 同源/跨源 AND、成本配额、专项压测 | 独立评审后实施 |

### 1.3 非目标

- 本设计不处理分钟级、盘口级实时信号；仍是盘后日线规则。
- 不执行下单，不把指标事件转换成交易建议。
- P0—P2 不接受任意表达式、脚本、SQL 或跨源 OR。
- 不在订阅执行过程中逐股票调用个股详情接口。

### 1.4 已确认产品与技术决策

| 决策编号 | 已确认结论 | 后端落地约束 |
| --- | --- | --- |
| D-01 | P0—P2 单订阅仅允许单一规则来源 | validator 拒绝多来源 payload；`COMPOSITE` 保留枚举但 B5 前不可创建或启用 |
| D-02 | 集合类首次执行只建立基线 | `notifyOnInitialMatch=false`；事务更新完整 `lastMatchCodes`，但不创建 ENTER hit、不投递通知 |
| D-03 | 周/月技术事件使用上次成功后的交易日窗口 | `previousSuccessfulTradeDate < eventTradeDate <= tradeDate`；首次执行只取当前交易日 |
| D-04 | 前端采用独立规则工作台 | API 设计保持无界面状态依赖；validate/preview/create 可被独立页面分步调用 |
| D-05 | 每用户保留 10 条订阅配额 | 查询当前用户全部未删除订阅计数，`ACTIVE/PAUSED/ERROR` 均计入，删除后释放 |
| D-06 | P2 仅支持盘后日线技术事件 | B3 只消费日级快照/事件表；拒绝分钟、盘口、实时事件 metricId |
| D-07 | v1 协议按本文冻结 | 实现中只允许新增可选响应字段；必填字段、枚举语义或默认值变化必须升协议版本 |
| D-08 | 指标语义由单一服务和 Metric Catalog 管理 | stock-analysis、stock-screener、subscription 共用 `TechnicalSignalDefinitionService`，禁止复制判定逻辑 |
| D-09 | READY 由数据事实决定，不由同步日志单独决定 | `SubscriptionDataReadinessService` 同时校验任务成功、水位、覆盖率和批次状态 |
| D-10 | B0 正确性先于新规则类型 | >500、point-in-time、幂等、首次基线用例未通过时，不启用 B2/B3 功能开关 |

## 二、现状与问题

### 2.1 已有能力

当前 `ScreenerSubscriptionController` 已有 10 个 POST 端点：

```text
list / detail / create / update / delete
pause / resume / run / logs / validate
```

已有状态为 `ACTIVE/PAUSED/ERROR`；连续失败达到阈值后进入 ERROR；BullMQ 支持批量调度与单条执行；事件网关已发送 `screener_subscription_alert` 和 `screener_subscription_failed`。

股票筛选服务已支持估值、财务、规模、行情、资金与部分技术条件，并已有 `minBuySignalCount`。因子模块已有 33 个内置因子、自定义因子、比较运算与 Top/Bottom 分位。股票详情已有多空信号摘要和技术事件计算逻辑。

### 2.2 已确认的正确性问题

| 编号 | 当前实现 | 问题 | 后果 |
| --- | --- | --- | --- |
| C-01 | processor 固定 `pageSize: 500`，把返回 items 当全量 | 命中超过 500 时集合被截断 | 产生大批虚假退出，后续永远看不到 500 名以后的代码 |
| C-02 | job 有 `tradeDate`，`stockService.screener` 未显式接收并贯穿该日期 | 底层读取各表“最新行” | 日志交易日和实际数据时点可能不同，无法复现 |
| C-03 | 财务过滤未以公告日做 point-in-time 限制 | 可能使用执行日之后才公告的数据 | 历史预览产生前视偏差 |
| C-04 | 首次执行 previousCodes 为空 | 当前全部命中被当成 new entry | 首次通知爆量，不符合“新进入”语义 |
| C-05 | 周一/月 1 日自然日定时 | 节假日、周期开始执行，且仅看当天事件 | 周/月规则时点不稳；短期技术事件会漏报 |
| C-06 | 批量 job 内串行直接执行全部订阅 | 单个慢规则拖住整个批次 | 扩展指标后吞吐和失败隔离不足 |
| C-07 | 更新订阅只保留当前 filters，无 rule version | 历史日志无法确定当时规则 | 无法审计、回放与精确去重 |
| C-08 | 通知只有代码数组 | 无前值/现值/原因 | 用户无法验证为何触发 |
| C-09 | MA/BOLL 等不同模块存在近似或不同口径 | 同名信号可能不一致 | 页面、预览、定时执行结论冲突 |
| C-10 | 成功更新、日志创建、通知不是一个可靠闭环 | 中间失败可能造成状态与日志不一致 | 重跑时重复或漏发通知 |

### 2.3 必须保持的现有行为

- 所有 Controller 接口保持 POST，参数走 Body。
- 所有查询都按 JWT `user.id` 隔离；用户不可通过订阅 ID 读取他人数据。
- `filters/strategyId/sortBy/sortOrder` 在迁移期继续可读写，保证存量订阅不中断。
- 10 条订阅配额首期不变。
- 三次连续失败转 ERROR 的策略保留，但数据未就绪不计为业务失败。

## 三、领域模型与规则协议

### 3.1 规则类型

```ts
export enum SubscriptionRuleType {
  STOCK_SCREENING = 'STOCK_SCREENING',
  FACTOR_SCREENING = 'FACTOR_SCREENING',
  SIGNAL_EVENT = 'SIGNAL_EVENT',
  COMPOSITE = 'COMPOSITE',
}

export type SubscriptionRuleSpec =
  | StockScreeningRuleSpec
  | FactorScreeningRuleSpec
  | SignalEventRuleSpec
  | CompositeRuleSpec;
```

JSONB 中必须保留 `type` 和 `version`。任何执行前先经过 `RuleSpecValidatorService`；不得把 JSONB 直接展开后传给 Prisma/SQL。

### 3.2 通用股票范围

```ts
export type UniverseSpec =
  | { type: 'ALL_A'; excludeSt: boolean; excludeSuspended: boolean; excludeBse: boolean }
  | { type: 'INDEX'; indexCode: string; excludeSt: boolean; excludeSuspended: boolean }
  | { type: 'WATCHLIST_GROUP'; groupId: number; excludeSt: boolean; excludeSuspended: boolean }
  | { type: 'FIXED'; tsCodes: string[] };
```

约束：

- `FIXED.tsCodes` 1—100 个且全部标准化为大写 `000001.SZ` 格式。
- `WATCHLIST_GROUP` 执行时必须带 userId 查询，fingerprint/cache key 也必须包含 userId。
- 指数成分以 `tradeDate` 当日有效成分为准；无历史有效期数据时先不开放该范围。
- P0 只开放当前数据已能精确支持的 `ALL_A/WATCHLIST_GROUP/FIXED`。

### 3.3 基础选股规则

```ts
export interface StockScreeningRuleSpec {
  type: SubscriptionRuleType.STOCK_SCREENING;
  version: 1;
  universe: UniverseSpec;
  filters: StockScreenerFilters;
}
```

`StockScreenerFilters` 由现有 `StockScreenerQueryDto` 抽取为共享 domain 类型。Controller DTO 负责 class-validator，domain 类型不依赖 Swagger。禁止订阅模块复制一份字段定义。

### 3.4 因子规则

```ts
export type FactorOperator =
  | 'GT'
  | 'GTE'
  | 'LT'
  | 'LTE'
  | 'BETWEEN'
  | 'TOP_PERCENT'
  | 'BOTTOM_PERCENT';

export interface FactorConditionSpec {
  factorId: string;
  operator: FactorOperator;
  value: number | [number, number];
}

export interface FactorScreeningRuleSpec {
  type: SubscriptionRuleType.FACTOR_SCREENING;
  version: 1;
  universe: UniverseSpec;
  conditions: FactorConditionSpec[];
  sortBy?: string;
  sortOrder?: 'ASC' | 'DESC';
}
```

约束：1—10 个条件；factorId 必须存在、已启用、当前用户有权读取；Top/Bottom 百分位为 `(0, 100]`；相同 factorId 首期只允许一次。

### 3.5 技术事件规则

```ts
export type SignalEventType =
  | 'GOLDEN_CROSS'
  | 'DEATH_CROSS'
  | 'OVERBOUGHT_ENTER'
  | 'OVERSOLD_ENTER'
  | 'BREAK_UP'
  | 'BREAK_DOWN'
  | 'BULLISH_STATE_ENTER'
  | 'BEARISH_STATE_ENTER'
  | 'VOLUME_EXPAND'
  | 'VOLUME_SHRINK'
  | 'SCORE_CROSS_UP'
  | 'SCORE_CROSS_DOWN';

export interface SignalConditionSpec {
  metricId: string;
  eventType: SignalEventType;
  threshold?: number;
  strengthAtLeast?: number;
}

export interface SignalEventRuleSpec {
  type: SubscriptionRuleType.SIGNAL_EVENT;
  version: 1;
  universe: UniverseSpec;
  conditions: SignalConditionSpec[];
  minSatisfied: number;
}
```

约束：1—10 个条件；`minSatisfied` 为 `1..conditions.length`；metricId/eventType 组合必须由 Metric Catalog 明确允许。

### 3.6 触发规则

```ts
export interface SubscriptionTriggerSpec {
  mode: 'ENTER' | 'EXIT' | 'BOTH' | 'EVENT';
  notifyOnInitialMatch: boolean;
  eventWindow: 'CURRENT_TRADE_DATE' | 'SINCE_LAST_SUCCESS';
  cooldownTradingDays: number;
  maxHitsPerNotification: number;
}
```

默认值：

| rule type | mode | notifyOnInitialMatch | eventWindow |
| --- | --- | --- | --- |
| STOCK_SCREENING | ENTER | false | CURRENT_TRADE_DATE |
| FACTOR_SCREENING | ENTER | false | CURRENT_TRADE_DATE |
| SIGNAL_EVENT | EVENT | true | DAILY 为 CURRENT；WEEKLY/MONTHLY 为 SINCE_LAST_SUCCESS |

`cooldownTradingDays` 首期固定 0；字段先纳入协议以便后续防重复事件。`maxHitsPerNotification` 默认 20、范围 1—100，只控制通知摘要，不截断持久化 hit。

### 3.7 Metric Catalog

Metric Catalog 是页面、校验器、评估器共享的指标白名单，不是简单前端 labelMap。

```ts
export interface MetricDefinition {
  id: string;
  version: number;
  source: 'STOCK' | 'FACTOR' | 'SIGNAL';
  category: string;
  label: string;
  description: string;
  valueType: 'NUMBER' | 'PERCENT' | 'ENUM' | 'BOOLEAN' | 'EVENT';
  unit?: string;
  operators: string[];
  enumOptions?: Array<{ value: string; label: string }>;
  min?: number;
  max?: number;
  precision?: number;
  requiredDataSets: string[];
  availability: 'ENABLED' | 'DISABLED' | 'DATA_NOT_READY';
  semanticsVersion: string;
}
```

实现位置建议：

```text
src/apps/screener-subscription/metric-catalog/
├─ metric-catalog.service.ts
├─ stock-metric.definitions.ts
├─ factor-metric.adapter.ts
├─ signal-metric.definitions.ts
└─ metric-catalog.types.ts
```

基础筛选字段先由静态白名单适配现有 DTO；因子定义从 Factor Registry 合并；自定义因子按当前用户动态追加；信号定义必须指向唯一计算器版本。

### 3.8 v1 版本策略（已冻结）

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| `ruleSpec.version` | v1 固定为整数 `1`；必填字段、枚举语义或规范化规则变化时升主版本 | `1` |
| `triggerSpec` | 沿用 ruleSpec 协议代际；v1 只允许增加可选字段，不删除或改变现有默认值 | `mode=ENTER` |
| `MetricDefinition.version` | 单指标元数据结构版本，非计算语义版本 | `1` |
| `semanticsVersion` | 使用 `<metricId>.v<major>`；判定、窗口、参数默认值任一变化都升 major | `macd.v1` |
| `catalogVersion` | 对当前用户可见目录规范化后计算 SHA-256，格式 `catalog-v1-<前12位>` | `catalog-v1-a13f09c72b81` |
| `dataVersions` | 记录实际读取的数据水位或快照批次 ID，不能写应用部署版本 | `daily=20260801`、`technical=20260801-batch-2` |
| `ruleFingerprint` | 包含规范化 ruleSpec 和全部相关 `semanticsVersion`，不包含 UI 顺序外的展示字段 | 64 位 SHA-256 hex |

冻结边界：create/update/preview/正式执行必须调用同一 normalizer、validator 和 fingerprint service。前端提交旧 `catalogVersion` 时，validate 返回 warning；若相关 metric 语义已变化则返回 `METRIC_VERSION_CONFLICT`，要求重新预览，不能静默升级规则。

## 四、API 设计

### 4.1 新增/扩展端点

| POST 端点 | Body | Response | 说明 |
| --- | --- | --- | --- |
| `/screener-subscription/metrics` | `{ sources?, catalogVersion? }` | 指标目录与版本 | 自定义因子按 user 隔离 |
| `/screener-subscription/preview` | rule/trigger/tradeDate? | 命中摘要、证据、数据版本 | 不写订阅状态，不发通知 |
| `/screener-subscription/hits` | `{ id, logId, page, pageSize, kind? }` | 分页 hit | 详情证据 |
| `/screener-subscription/run/status` | `{ jobId }` | QUEUED/RUNNING/SUCCESS/FAILED | 手动执行追踪 |

现有 `create/update/detail/list/logs/validate/run` 扩展字段，不新增 v2 URL。全部保持 POST + Body。

### 4.2 Create/Update DTO

```ts
export interface CreateSubscriptionRequest {
  name: string;
  frequency: 'DAILY' | 'WEEKLY' | 'MONTHLY';
  status?: 'ACTIVE' | 'PAUSED';
  ruleSpec: SubscriptionRuleSpec;
  triggerSpec?: Partial<SubscriptionTriggerSpec>;
  notificationSpec?: {
    inApp: boolean;
    maxHitsPerNotification?: number;
  };

  // 迁移期兼容；新客户端不得与 ruleSpec 同时提交
  filters?: StockScreenerFilters;
  strategyId?: number;
  sortBy?: string;
  sortOrder?: 'asc' | 'desc';
}

export interface UpdateSubscriptionRequest extends Partial<CreateSubscriptionRequest> {
  id: number;
  expectedUpdatedAt?: string;
}
```

规则更新时：

1. 规范化并校验 ruleSpec。
2. 计算新 fingerprint。
3. fingerprint 变化则 `ruleVersion + 1`，清空 `lastMatchCodes`，下一次视为新基线。
4. 只改名称/频率/通知设置时不增加规则版本。
5. `expectedUpdatedAt` 不匹配返回 `SUBSCRIPTION_CONFLICT`，防止双页面覆盖。

### 4.3 Preview DTO

```ts
export interface PreviewSubscriptionRequest {
  ruleSpec: SubscriptionRuleSpec;
  triggerSpec?: Partial<SubscriptionTriggerSpec>;
  tradeDate?: string; // YYYYMMDD；为空取最新已就绪交易日
  limit?: number;     // 展示限制 1..100，默认 20
}

export interface PreviewSubscriptionResponse {
  ruleFingerprint: string;
  catalogVersion: string;
  asOfTradeDate: string;
  universeCount: number;
  matchedCount: number;
  truncated: boolean;
  matchedStocks: Array<{ tsCode: string; name: string; industry?: string }>;
  evidence: SubscriptionHitEvidenceDto[];
  warnings: Array<{ code: string; message: string }>;
  dataVersions: Record<string, string>;
  executionMs: number;
}
```

`truncated` 仅表示响应展示数组截断；`matchedCount` 必须是完整集合数量。preview 与正式执行调用同一 evaluator，不允许维护两套 SQL。

### 4.4 结构化错误

| HTTP | code | 场景 | consecutiveFails |
| --- | --- | --- | --- |
| 400 | `RULE_INVALID` | DTO/指标/运算符/范围错误 | 不适用 |
| 400 | `RULE_SOURCE_CONFLICT` | ruleSpec 与 legacy filters 同时传 | 不适用 |
| 404 | `SUBSCRIPTION_NOT_FOUND` | 不存在或不属于用户 | 不适用 |
| 409 | `SUBSCRIPTION_CONFLICT` | 乐观并发失败 | 不适用 |
| 409 | `COOLDOWN` | 手动执行冷却 | 不增加 |
| 422 | `DATA_NOT_READY` | 指定交易日快照未完成 | 不增加；run 标记 skipped |
| 422 | `METRIC_DISABLED` | 指标已停用 | 正式任务增加，第三次 ERROR |
| 429 | `SUBSCRIPTION_QUOTA_EXCEEDED` | 超 10 条配额 | 不适用 |
| 500 | `EVALUATION_FAILED` | SQL/计算异常 | 增加 |

错误响应延续全局异常格式，`details` 只放可公开字段，不返回 SQL、堆栈或内部表名。

### 5.2 统一接口

```ts
export interface EvaluationContext {
  userId: number;
  tradeDate: string;
  previousSuccessfulTradeDate: string | null;
  ruleVersion: number;
  preview: boolean;
}

export interface EvaluationOutcome {
  asOfTradeDate: string;
  universeCount: number;
  matchedCodes: string[];
  eventCandidates: Array<{
    tsCode: string;
    eventKey: string;
    metricId: string;
    eventType: string;
    eventTradeDate: string;
  }>;
  dataVersions: Record<string, string>;
  warnings: Array<{ code: string; message: string }>;
}

export interface SubscriptionEvaluator<TSpec extends SubscriptionRuleSpec> {
  readonly type: TSpec['type'];
  evaluate(ctx: EvaluationContext, spec: TSpec): Promise<EvaluationOutcome>;
  explain(
    ctx: EvaluationContext,
    spec: TSpec,
    candidates: Array<{ tsCode: string; kind: string; eventKey?: string }>,
  ): Promise<SubscriptionHitEvidence[]>;
}
```

集合评估器返回完整 `matchedCodes`，由 Trigger Planner 对比上次集合；事件评估器返回 eventCandidates。证据仅为实际触发项批量计算，避免为数千个未变化的匹配生成大 JSON。

### 5.3 Registry 与分派

```ts
@Injectable()
export class SubscriptionEvaluatorRegistry {
  private readonly evaluators = new Map<SubscriptionRuleType, SubscriptionEvaluator<SubscriptionRuleSpec>>();

  get(type: SubscriptionRuleType): SubscriptionEvaluator<SubscriptionRuleSpec> {
    const evaluator = this.evaluators.get(type);
    if (!evaluator) throw new RuleUnsupportedException(type);
    return evaluator;
  }
}
```

禁止 processor 继续直接依赖 `StockService`。processor 只负责加载订阅、建立运行记录、调用 registry、规划 trigger、事务写入和投递通知任务。

### 5.4 Processor 流程

```text
1. 以 subscriptionId + tradeDate + ruleVersion 获取/创建 run
2. 若同 key 已 SUCCESS：直接返回；若 RUNNING：拒绝重复领取
3. 加载 ACTIVE 订阅，解析 effectiveRuleSpec
4. 校验 ruleSpec 与指标目录版本
5. 检查所需数据集对 tradeDate 已 READY
6. evaluator.evaluate(ctx, spec)
7. TriggerPlanner：
   - 集合规则：计算 ENTER/EXIT；首次执行按 notifyOnInitialMatch 决定 hit
   - 事件规则：按 eventWindow 过滤并按 eventKey 去重
8. evaluator.explain(...) 批量生成实际触发证据
9. 单事务：插入 hits、完成 log、更新 lastMatchCodes/lastRunResult/lastRunAt
10. 事务提交后投递 notification job；通知成功回写 hit.notifiedAt
```

业务事务失败不得更新 `lastMatchCodes`。通知失败不回滚评估结果，由独立队列重试，避免重新评估和重复 hit。

## 六、各评估器实现

### 6.1 Stock Screening Evaluator

在 stock 模块新增内部方法，不经分页 Controller DTO：

```ts
export interface ScreenCodesOptions {
  userId: number;
  tradeDate: string;
  universe: UniverseSpec;
  filters: StockScreenerFilters;
}

export interface ScreenCodesResult {
  universeCount: number;
  matchedCodes: string[];
  dataVersions: Record<string, string>;
}

screenCodes(options: ScreenCodesOptions): Promise<ScreenCodesResult>;
```

现有 `screener()` 改为：先调用同一 Query Builder 得到 filtered codes/count，再做排序和分页 hydrate。订阅评估器直接取完整 code 集合，不允许传 `pageSize: 500` 规避。

#### 交易日 SQL 原则

所有数据源都显式约束 `<= :tradeDate`，并用窗口函数取每只股票截至该日最新一行：

```sql
WITH latest_daily AS (
  SELECT *
  FROM (
    SELECT d.*,
           ROW_NUMBER() OVER (PARTITION BY d.ts_code ORDER BY d.trade_date DESC) AS rn
    FROM stock_daily d
    WHERE d.trade_date <= :tradeDate
  ) x
  WHERE x.rn = 1
),
latest_factor AS (
  SELECT *
  FROM (
    SELECT f.*,
           ROW_NUMBER() OVER (PARTITION BY f.ts_code ORDER BY f.trade_date DESC) AS rn
    FROM stk_factor f
    WHERE f.trade_date <= :tradeDate
  ) x
  WHERE x.rn = 1
),
latest_finance AS (
  SELECT *
  FROM (
    SELECT q.*,
           ROW_NUMBER() OVER (
             PARTITION BY q.ts_code
             ORDER BY q.ann_date DESC, q.end_date DESC
           ) AS rn
    FROM finance_indicator q
    WHERE q.ann_date <= :tradeDate
  ) x
  WHERE x.rn = 1
)
SELECT b.ts_code
FROM stock_basic b
JOIN latest_daily d ON d.ts_code = b.ts_code
LEFT JOIN latest_factor f ON f.ts_code = b.ts_code
LEFT JOIN latest_finance q ON q.ts_code = b.ts_code
WHERE /* 只拼接白名单字段对应的参数化谓词 */;
```

真实表名按现有 Prisma map 调整。关键约束是财务指标必须使用 `ann_date <= tradeDate`，不能只看报告期 `end_date`。

#### 技术筛选语义

`maTrend`、BOLL、MACD 等条件必须调用 B3 建立的共享技术语义函数，不能保留“close > MA20 且 DIF > 0”冒充完整均线多头排列。旧语义在 catalog 中标记版本，新订阅只用新版本；存量规则迁移时记录 warning。

### 6.2 Factor Screening Evaluator

在 factor 模块提取无分页内部能力：

```ts
screenCodes(input: {
  userId: number;
  tradeDate: string;
  universe: UniverseSpec;
  conditions: FactorConditionSpec[];
}): Promise<{
  universeCount: number;
  matchedCodes: string[];
  factorSnapshotVersion: string;
}>;
```

执行步骤：

1. 校验 tradeDate 为交易日。
2. 对所有 factorId 检查当日 snapshot coverage；缺任一必要因子抛 `DATA_NOT_READY`，不能返回空集。
3. 解析 universe 得到基础代码集合。
4. 普通阈值直接参数化过滤；Top/Bottom 使用 `PERCENT_RANK` 或已有排名快照。
5. 多条件取交集，返回完整 codes。
6. explain 对触发股票批量返回因子值、分位、阈值、排名和快照版本。

Top/Bottom 的分母是规则 universe 内有有效因子值的股票数；缺失值不计入分母，必须在 Metric Catalog 说明。

### 6.3 Signal Event Evaluator

不能复用“逐股详情查询”执行全市场规则。新增盘后批量作业，在日线、stk_factor 等数据就绪后按股票分片计算并写入快照/事件。

#### 计算顺序

```text
18:30 数据同步
20:00 因子预计算
20:05 技术信号快照/事件计算
20:30 条件订阅 dispatcher（先过 readiness gate）
```

#### 首批统一语义

| metricId | 事件 | 判定必须使用的数据 |
| --- | --- | --- |
| `macd` | GOLDEN_CROSS / DEATH_CROSS | 前/当前 DIF、DEA；严格穿越，不以当前 DIF>DEA 代替 |
| `kdj` | GOLDEN_CROSS / DEATH_CROSS | 前/当前 K、D；可在 catalog 声明低位/高位限制 |
| `rsi6` | OVERSOLD_ENTER / OVERBOUGHT_ENTER | 前值位于区间外、当前进入 `<30` 或 `>70` |
| `boll` | BREAK_UP / BREAK_DOWN | 前/当前 close 与 upper/lower；明确是否要求前值在轨内 |
| `ma_alignment` | BULLISH/BEARISH_STATE_ENTER | MA5/10/20/60 完整排列从 false→true |
| `sar` | BULLISH/BEARISH_STATE_ENTER | close 与 SAR 关系发生翻转 |
| `volume_ratio_20` | VOLUME_EXPAND/SHRINK | 当前量 / 前 20 有效交易日均量，停牌日处理一致 |

`stock-analysis`、`stock-screener` 和 subscription 必须引用同一 `TechnicalSignalDefinitionService`；个股详情展示可以格式化，但不得重写判定。

#### 事件窗口

- DAILY：`eventTradeDate = tradeDate`。
- WEEKLY/MONTHLY + `SINCE_LAST_SUCCESS`：`previousSuccessfulTradeDate < eventTradeDate <= tradeDate`。
- 首次执行没有 previousSuccessfulTradeDate 时，只查询 `eventTradeDate = tradeDate`，防止回溯历史爆量。
- 多个条件要求 `minSatisfied > 1` 时，以 `tsCode + eventTradeDate` 分组统计；不同日期发生的事件不得拼成一次组合命中。

### 6.4 Composite Evaluator（P3）

首期只允许：

```ts
interface CompositeRuleSpec {
  type: 'COMPOSITE';
  version: 1;
  logic: 'AND';
  children: Array<StockScreeningRuleSpec | FactorScreeningRuleSpec | SignalEventRuleSpec>;
}
```

限制 children 2—3 个，先各自评估，再按代码集合求交集。包含事件子规则时，以事件日期为锚点，其他集合规则在该日期评估。未具备历史 point-in-time 能力的数据源不得加入 composite。

## 八、调度、数据就绪与幂等

### 8.1 调度改造

用一个交易日 dispatcher 取代“周一/月 1 日直接跑”：

```ts
@Cron('0 30 20 * * 1-5', { timeZone: 'Asia/Shanghai' })
async dispatchForTradeDate(): Promise<void> {
  const tradeDate = await tradeCalendar.latestOpenDateReadyForSubscription();
  if (!tradeDate || tradeDate === await this.lastDispatchedDate()) return;

  const frequencies = [SubscriptionFrequency.DAILY];
  if (await tradeCalendar.isLastOpenDayOfWeek(tradeDate)) frequencies.push(SubscriptionFrequency.WEEKLY);
  if (await tradeCalendar.isLastOpenDayOfMonth(tradeDate)) frequencies.push(SubscriptionFrequency.MONTHLY);

  for (const frequency of frequencies) await this.enqueueBatch(frequency, tradeDate);
}
```

若周/月最后交易日因同步失败未执行，下一次数据恢复时允许补跑该周期，不能简单用自然日判断跳过。

### 8.2 批次拆分

Batch job 只分页读取 subscription IDs，并为每条订阅 enqueue `EXECUTE_SUBSCRIPTION`；不得在一个 worker 循环中直接执行全部规则。

建议 jobId：

```text
subscription:{subscriptionId}:{tradeDate}:v{ruleVersion}
```

BullMQ 同 key 防重复只是第一道防线，数据库 run unique 和 hit unique 是最终防线。

### 8.3 Data Readiness Gate

```ts
interface DataReadinessResult {
  ready: boolean;
  tradeDate: string;
  dataVersions: Record<string, string>;
  missing: string[];
}

check(requiredDataSets: string[], tradeDate: string): Promise<DataReadinessResult>;
```

READY 判定统一收口到 `SubscriptionDataReadinessService`。`TushareSyncLog.SUCCESS` 只作为任务完成证据，不能单独把数据集判为 READY；最终判定必须同时满足实际表水位、覆盖率和派生批次状态。

| 数据集键 | READY 来源 | 已确认门槛 | `dataVersions` 写法 |
| --- | --- | --- | --- |
| `MARKET_DAILY` | 同步日志 + `stock_daily` 实际水位/覆盖 | tradeDate 同步成功；可交易 universe 有行情或明确停牌原因，覆盖率 `>=99.5%` | `tradeDate:syncLogId` |
| `FINANCIAL_PIT` | 财务同步水位 + `ann_date` 可见性 | 最近成功财务批次存在；查询严格 `ann_date <= tradeDate`，不要求每只股票当天有新财报 | `maxAnnDate:syncLogId` |
| `FACTOR_SNAPSHOT` | 因子预计算批次 + 因子快照表 | 所有必需 factorId 批次 SUCCESS；各因子在规则 universe 的有效覆盖率 `>=99.0%` | `tradeDate:batchId` |
| `TECHNICAL_SIGNAL` | 技术快照批次 manifest + 快照/事件表 | 批次 SUCCESS；可交易股票快照覆盖率 `>=99.5%`；事件写入事务已提交 | `tradeDate:batchId:catalogVersion` |
| `WATCHLIST/INDEX_MEMBERS` | 分组更新时间或历史成分有效期 | WATCHLIST 读取当前用户分组版本；INDEX 必须有覆盖 tradeDate 的有效期数据 | `groupUpdatedAt` 或 `effectiveBatchId` |

低于门槛时返回 `DATA_NOT_READY`，details 只包含 `missing`、实际覆盖率、最近可用日期和下一次重试时间。run 标记 `SKIPPED_DATA_NOT_READY`，不更新 `lastMatchCodes`、不增加 `consecutiveFails`；按 5/15/30 分钟退避重试，22:30 后停止当晚自动重试并发送一次“数据延迟”通知。次日 READY 后补跑原交易日，仍使用原 `runKey`，确保不重复 hit。

### 8.4 通知可靠性

1. 业务事务写入 hit 后，enqueue `SEND_SUBSCRIPTION_NOTIFICATION`。
2. 通知 worker 查询 `notifiedAt IS NULL` 的 hits，按 maxHitsPerNotification 生成摘要。
3. 站内消息持久化成功后再通过 WebSocket 提醒客户端刷新。
4. 回写 notifiedAt；job 失败按指数退避重试。
5. 同一 hit 不重复通知；额外命中只显示“另有 N 条”，不丢失详情数据。

推荐统一事件：

```ts
interface ScreenerSubscriptionTriggeredEvent {
  subscriptionId: number;
  subscriptionName: string;
  ruleType: SubscriptionRuleType;
  tradeDate: string;
  triggerCount: number;
  kinds: Array<'ENTER' | 'EXIT' | 'EVENT'>;
  preview: Array<{
    tsCode: string;
    name?: string;
    kind: string;
    reason: string;
  }>;
}
```

保留旧 `screener_subscription_alert` 一个版本周期；新客户端改订阅 `screener_subscription_triggered`。

## 九、安全、性能与可观测性

### 9.1 安全与隔离

- service 每次通过 `{ id, userId }` 查询订阅；对不存在与越权统一返回 NOT_FOUND。
- 自定义 factorId 必须校验 owner/visibility，不因知道 ID 即可订阅。
- ruleSpec JSON 最大 32KB；factor/signal 条件最多 10；fixed codes 最多 100。
- Metric Catalog 不返回内部 SQL、函数名或敏感数据源凭证。
- 日志记录 fingerprint、ruleType、指标 ID，不记录完整自定义研究规则值；错误信息脱敏。
- 所有动态 SQL 只从白名单列映射生成，数值始终参数化。

### 9.2 性能策略

- 全市场 code 集合约数千项，可在单次评估内完整放入内存；禁止为方便分页牺牲正确性。
- 详情 hydrate 与 evidence 必须批量查询，不允许 N+1。
- 相同 `tradeDate + fingerprint + userScope` 可用 Redis 缓存评估集合，TTL 48 小时；WATCHLIST 需纳入 userId 和 group updatedAt。
- processor 并发从 2 开始，根据数据库 P95 调整；单用户可同时运行不超过 2 条重规则。
- preview 每用户限频，推荐 10 次/分钟；300ms 内的规则编辑由前端防抖，后端仍需限流。
- 因子和信号快照查询建立 `(trade_date, metric/factor)`、`(ts_code, trade_date)` 复合索引。

### 9.3 指标

```text
screener_subscription_run_total{rule_type,status,frequency}
screener_subscription_run_duration_seconds{rule_type}
screener_subscription_match_count{rule_type}
screener_subscription_trigger_count{rule_type,kind}
screener_subscription_data_lag_days{dataset}
screener_subscription_notification_total{status}
screener_subscription_queue_wait_seconds{job_name}
technical_signal_snapshot_duration_seconds
technical_signal_snapshot_coverage_ratio
```

标签只能使用低基数枚举，禁止 subscriptionId/userId/metricId 直接作为 Prometheus label。日志可带 subscriptionId、jobId、tradeDate、ruleVersion、fingerprintPrefix 和 traceId。

### 9.4 SLO 建议

| 项目 | 目标 |
| --- | --- |
| 盘后日频订阅完成 | 数据 READY 后 30 分钟内 99% 完成 |
| 单规则评估 P95 | 基础/因子 `<3s`，技术事件 `<2s` |
| preview P95 | `<3s`；超时 10s |
| 技术快照覆盖率 | 可交易股票 `>=99.5%`，剩余有缺失原因 |
| 重复 hit/通知 | 0 |

```json
  "type": "STOCK_SCREENING",
  "version": 1,
  "universe": { "type": "ALL_A", "excludeSt": true, "excludeSuspended": true, "excludeBse": false },
  "filters": "<legacy filters>"
}
```

3. 计算 ruleFingerprint，设置 `ruleType=STOCK_SCREENING`、默认 triggerSpec。
4. 双读：`ruleSpec != null` 优先；否则运行时适配 legacy filters 并记录迁移 warning。
5. Feature flag 先对测试用户启用新 processor，再灰度到全部用户。
6. 稳定两个完整交易周后停止创建 legacy-only 订阅；legacy columns 最早下一个大版本再评估删除。

### 10.2 回滚

- 关闭 `SCREENER_SUBSCRIPTION_RULE_ENGINE_V2` 后，STOCK_SCREENING 仍可回退 legacy filters executor。
- FACTOR_SCREENING/SIGNAL_EVENT 在旧 executor 下自动 PAUSED，返回明确兼容提示，不转换为基础 filters。
- 新表只增不删，回滚不丢历史 hit；旧前端可通过 detail 中的 `ruleSummary` 只读展示新规则。
- 数据库迁移回滚不立即 drop enum/table；使用向前修复，避免删除用户研究记录。

## 十一、测试设计

### 11.1 单元测试

- Rule normalizer：key 顺序、股票代码排序、数值精度产生稳定 fingerprint。
- Rule validator：未知 type/metric/operator、越界百分位、minSatisfied、规则过大。
- Trigger Planner：首次基线、ENTER/EXIT/BOTH、事件窗口、notifyOnInitialMatch。
- Scheduler：节假日、周最后交易日、月最后交易日、数据延迟补跑。
- Error policy：DATA_NOT_READY 不累计失败；EVALUATION_FAILED 第三次转 ERROR。

### 11.2 集成测试

| 用例 | 验证点 |
| --- | --- |
| >500 命中两次执行 | matchCount 为完整值，第二次无虚假 EXIT |

| 订阅删除 | logs/hits 级联删除，其他用户数据不受影响 |

### 12.3 完成定义

本方案完成不是“接口能返回”，而是满足以下闭环：

1. 同一规则、同一交易日，预览与定时执行结果一致。
2. 任意运行都能说明使用了哪个交易日、哪些数据版本、哪版规则。
3. 任意提醒都能展示可复核证据，重复 job 不重复提醒。
4. 数据未就绪不会被误记成 0 命中或用户规则失败。
5. 存量订阅无需用户重建即可继续执行，并可安全回滚。
