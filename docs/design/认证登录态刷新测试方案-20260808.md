## 2. 复现事实

- 2026-08-08 09:44 左右，Chrome 中刚登录的 `superadmin` 开始真实 Agent 回归。
- 通过 UI 连续创建 4 个独立会话；前三个产生 Run，第四个会话创建后页面跳转 `/sign-in`。
- 已落库会话均为 `user_id=1`、`account=superadmin`、`MANUAL / gpt-5.6-terra`。
- 登录后仅数分钟即掉线，明显短于 Controller 契约注明的 Access Token 30 分钟寿命。
- 此问题优先于继续 10×10 Agent 浏览器回归处理。

## 3. 业务规则与不变量

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| R-001 | 登录成功后，在 Access Token 有效期内不得因普通并发业务请求被清空身份 | 登录契约、用户预期 |
| R-002 | Access Token 过期后，浏览器应使用 HttpOnly Refresh Token 无感换取新 Token | `POST /api/auth/refresh` 契约 |
| R-003 | 同一页面多个并发 401 不得各自独立轮换 Refresh Token | 轮换 Token 的单次有效性与竞态安全 |
| R-004 | 首个刷新成功后，原失败请求应使用新 Access Token 至多重放一次 | 幂等与防无限重试 |
| R-005 | 只有 Refresh Token 缺失、过期、被撤销或刷新确定失败时才进入未登录态 | 登录态安全边界 |
| R-006 | Agent SSE/轮询/REST 并发不得导致误登出；长 Run 页面须保持可恢复 | 真实业务主链 |
| R-007 | Refresh Token Cookie 路径、SameSite、Secure 必须允许当前同源 `/api/auth/refresh` 使用 | Cookie 契约 |
| R-008 | 登录、刷新、登出和 401 恢复过程不得泄露 Token | 安全要求 |

## 4. 风险清单

| 风险 | 业务影响 | 优先级 |
| --- | --- | --- |
| 并发 401 触发多个 Refresh Token 轮换 | 后续请求携带已作废 Token，用户随机掉线 | P0 |
| 任意 401 直接清空身份，未先刷新 | 长任务和高并发页面频繁回登录页 | P0 |
| 刷新请求自身被 401 拦截器递归处理 | 无限刷新、重试风暴或误登出 | P0 |
| Cookie path/代理域名不一致 | Refresh Token 实际未随请求发送 | P0 |
| Access Token TTL 配置与注释/前端假设不一致 | “刚登录”即过期 | P0 |
| SSE 与普通请求使用不同 Token 更新路径 | 页面部分连接正常、部分请求 401 | P1 |
| 刷新成功但等待队列未正确恢复 | 随机请求失败或重复提交 | P1 |
| 服务重启/Redis 失联被错误解释为用户登出 | 外部故障与本地缺陷混淆 | P1 |

## 8. 执行结论

- 首要根因：React StrictMode 重放首屏副作用，导致 AuthProvider 启动恢复和登录页验证码初始化重复执行；此前浏览器回归又以整页刷新切换会话，放大 `/api/auth/refresh` 请求并触发限流。
- 二级根因：多个本地标签共享 HttpOnly Refresh Cookie，但前端“刷新失败”曾主动调用 logout 并广播 `SIGNED_OUT`，陈旧标签可能撤销或清空其他标签刚恢复的会话；服务端原先分两步“检查有效→标记已用”，并发请求可能同时看见 valid 并各自签发新 Refresh Token。
- 修复：AuthProvider 使用单飞 Promise 合并同一标签的一轮启动恢复，成功恢复主动广播 Token，失败时给同源标签 250ms 同步窗口；未授权只结束当前标签的内存会话，不调用 logout、不广播全局登出；只有用户明确退出才撤销共享 Cookie。登录页初始验证码请求增加幂等保护。服务端使用 Redis Lua 原子消费 Refresh Token，首次为 `valid`，并发重复为 `grace`。
- 自动化：客户端 Agent/认证/API 共 23 个测试文件、149 个测试通过；服务端认证/Token 3 个套件、64 个测试通过；两端 lint、TypeScript/构建通过。
- 真实证据一：超级管理员在 Chrome 中完成 10 个独立会话、每会话 10 条自然语言消息；2026-08-08 11:35:26 Access Token 真实过期后仅发生一次 `POST /api/auth/refresh 201`，页面保持登录并继续发送，未出现新的 429。
- 真实证据二：补丁热重载后，多个已打开的本地页面在 12:09:25 同秒发出 5 个刷新请求，服务端全部返回 201，没有 invalid/429；12:09:30 超级管理员 `userId=1` 继续读取 Agent 会话并返回 200。隔离 Redis 实测同一旧 Token 第一次返回 `valid`、第二次返回 `grace`，测试键随后删除。
