# 个股技术与数据可用性 Tool 后端设计

> 状态：✅ 代码实现与本地验收完成，生产灰度观察待执行  
> 基线：2026-08-05  
> 关联调研：[数据与智能体工具能力全景调研及补充规划](./数据与智能体工具能力全景调研及补充规划.md)  
> 实施范围：`get_stock_technical_indicators@1`、`get_stock_technical_signals@1`、`get_data_availability@1`、`screen_stocks@2`、Workflow v5、`stk_factor` 同步限流加固

## 1. 结论与实施边界

本期可以直接开发，不需要新增 Tushare 接口权限，也不需要先新增行情或技术因子表。

- 技术因子已经存于 PostgreSQL：Prisma Model 为 `StkFactor`，物理表为 `stock_technical_factors`。
- 2026-08-05 实测共有 18,218,428 行，数据截止 2026-08-04；主键为 `(tsCode, tradeDate)`，已有 `(tradeDate)` 和 `(tsCode, tradeDate DESC)` 索引。
- Agent 的技术指标和数据可用性 Tool 只读取 PostgreSQL。一次用户提问对应 **0 次 Tushare 请求**。
- Tushare 只出现在定时同步或人工回补链，禁止出现在 Agent Tool 运行时依赖图中。
- `StkFactor` 当前真实可用的首版指标组是 `MACD`、`KDJ`、`RSI`、`BOLL`。数据库中的 `cci_14`、`cci_20`、`tr`、`atr14`、`atr20`、`vr_26` 在全表实测均无非空值，v1 不对外承诺 CCI、ATR、VR。
- 标准技术信号使用现有本地 QFQ 确定性引擎和 14 个版本化信号定义，不把选股器现有启发式条件冒充为同一套标准事件。
- P0 不新增 Prisma migration；只有后续决定补存官方 `cci` 或其他专业因子时，才单独设计 schema 迁移。

本期不做：

- 不允许模型执行 SQL、Prisma、Tushare API 或自定义指标表达式。
- 不在 Agent 请求中现场向 Tushare 补数据。
- 不让模型自行计算或补造技术指标。
- 不把信号结果包装成投资建议或下单动作。
- 不破坏 `screen_stocks@1` 和 Workflow v1–v4 的历史可重放性。

## 2. 已核验现状

### 2.1 数据库存量

| 项目             | 当前事实                                  |
| ---------------- | ----------------------------------------- |
| Model / 表       | `StkFactor` / `stock_technical_factors`   |
| 行数             | 18,218,428                                |
| 数据截止         | 2026-08-04                                |
| 典型日全市场行数 | 约 5,500                                  |
| 主键             | `(tsCode, tradeDate)`                     |
| 查询索引         | `(tradeDate)`、`(tsCode, tradeDate DESC)` |
| 数据源           | Tushare 社区技术因子 `stk_factor`         |
| 复权语义         | 接口快照前复权，标记为 `FORWARD_SNAPSHOT` |

`600089.SH` 的最近记录已实测存在，2026-08-04 的 MACD、KDJ、RSI、BOLL 均有值。因此“查不到特变电工技术指标”不是数据缺失，而是 Agent 没有精确个股 Tool。

### 2.2 技术因子字段真实性

首版允许：

| 指标组 | 数据库字段                          |
| ------ | ----------------------------------- |
| MACD   | `macdDif`、`macdDea`、`macd`        |
| KDJ    | `kdjK`、`kdjD`、`kdjJ`              |
| RSI    | `rsi6`、`rsi12`、`rsi24`            |
| BOLL   | `bollUpper`、`bollMid`、`bollLower` |

首版禁止：

| 指标组 | 原因                                                               | 后续处理                                         |
| ------ | ------------------------------------------------------------------ | ------------------------------------------------ |
| CCI    | 当前请求字段和官方基础接口不一致，现有 `cci_14`、`cci_20` 全表为空 | 审计官方 `cci` 字段；需要存储时另开 migration    |
| ATR    | `tr`、`atr14`、`atr20` 全表为空                                    | 使用版本化本地计算或匹配的专业接口，不能返回伪 0 |
| VR     | `vr_26` 全表为空                                                   | 使用版本化本地计算或匹配的专业接口               |

字段为空时只能返回 `null` 和 warning，禁止用 `0`、模型推算或另一来源数据静默填充。

### 2.3 Tushare 调用链与风险

当前同步链：

```text
19:40 交易日调度 / 人工 full sync
  -> FactorDataSyncService.syncStkFactor()
  -> 按交易日串行循环
  -> FactorDataApiService.getStkFactorByTradeDate()
  -> TushareClient.call(api_name = stk_factor)
  -> 当日 deleteMany + createMany 事务
```

当前事实：

- 增量同步通常只请求 1 个开放交易日，近期单日约 5,500 行，低于官方单次 10,000 行上限。
- 最近一次两日增量同步写入 11,057 行，约 9.35 秒，没有失败。
- 全历史从 1990 年回补可能产生约 8,500 次请求，存在分钟频率限制风险。
- `TushareClient` 已有同 API 串行队列、跨 API 最大并发 5、错误码 `40203` 后等待 65 秒重试。
- 但 `DOCUMENTED_RATE_LIMIT_MS` 当前没有 `stk_factor`，因此主动间隔为 0 ms；`40203` 只是事后兜底，不能作为全量回补的主要限流方案。

Tushare 官方当前说明：`stk_factor` 单次最多 10,000 条；5000 积分每分钟 100 次，8000 积分以上每分钟 500 次；指标基于前复权数据。实施以 [Tushare `stk_factor` 官方文档](https://tushare.pro/document/2?doc_id=296) 为准。

## 3. 强制架构决策

### 3.1 数据路径隔离

```text
用户问题
  -> Workflow v5
  -> Tool Registry / Policy / Schema
  -> Agent Tool Adapter
      -> StockTechnicalToolFacade ---------> PostgreSQL StkFactor
      -> TechnicalSignalToolFacade --------> 本地 QFQ 引擎 + PostgreSQL
      -> DataAvailabilityToolFacade --------> PostgreSQL 元数据/质量/同步状态
      -> StockScreenerService --------------> PostgreSQL

定时/人工同步
  -> FactorDataSyncService
  -> FactorDataApiService
  -> TushareClient
  -> Tushare
```

必须满足：

1. `src/apps/agent/tools/**` 不得注入 `TushareClient` 或任何 `*ApiService`。
2. 三个新 Tool Facade 不得注入 `TushareClient` 或任何 `*ApiService`。
3. Tool 缺数据时返回 `DATA_NOT_FOUND` 或 `DATA_NOT_READY`，不得触发在线补数。
4. CI 增加架构测试，扫描上述目录的 import 和 Nest provider 依赖，防止未来回归。
5. 通过指标验证 `agent_tool_calls_total{tool_key=...}` 增长时，`tushare_requests_total{api_name="stk_factor"}` 不应相关增长。

### 3.2 来源不可混用

| 能力       | 唯一来源            | 来源标识                    |
| ---------- | ------------------- | --------------------------- |
| 预计算指标 | `StkFactor`         | `TUSHARE_STK_FACTOR`        |
| 标准信号   | 本地 QFQ 日线引擎   | `LOCAL_QFQ_OHLCV`           |
| 全市场筛选 | 现有筛选 SQL 启发式 | `STOCK_SCREENER_HEURISTICS` |

同一个 Tool 版本内不得按字段是否为空在不同来源间自动切换。需要扩展来源时发布新 Tool 版本，或新增显式 `source` 输入并重新定义数据版本。

### 3.3 日期约定

- Agent Tool 输入统一使用 ISO `YYYY-MM-DD`，与现有 Agent JSON Schema 保持一致。
- Facade 内部再转换为数据库或技术信号模块需要的 `YYYYMMDD`。
- `asOfDate` 省略时，使用当前数据库共同水位线对应的最近完整开放交易日。
- `asOfDate` 为周末、节假日、盘中或同步尚未完成日期时，解析到不晚于该日的最近 READY 交易日，并返回 `LATEST_READY_TRADE_DATE_USED`。
- 输出同时保留 `requestedAsOfDate` 和 `dataThrough`，不得把二者混为一谈。

## 4. `get_stock_technical_indicators@1`

### 4.1 职责

返回单只股票已经入库的技术指标事实。它不判定买卖信号，不调用本地计算引擎，不请求 Tushare。

### 4.2 输入 JSON Schema

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["tsCode"],
  "properties": {
    "tsCode": {
      "type": "string",
      "pattern": "^\\d{6}\\.(SH|SZ|BJ)$"
    },
    "asOfDate": {
      "type": "string",
      "format": "date"
    },
    "lookback": {
      "type": "integer",
      "minimum": 1,
      "maximum": 500,
      "default": 2
    },
    "indicators": {
      "type": "array",
      "minItems": 1,
      "maxItems": 4,
      "uniqueItems": true,
      "items": {
        "enum": ["MACD", "KDJ", "RSI", "BOLL"]
      },
      "default": ["MACD", "KDJ", "RSI", "BOLL"]
    }
  }
}
```

不保留 `includeSeries`：`lookback=1` 就是快照，`lookback>1` 就是短序列，避免两个输入表达同一含义。

### 4.3 输出 `data`

```ts
interface StockTechnicalIndicatorsData {
  tsCode: string
  requestedAsOfDate: string | null
  dataThrough: string
  coverageStart: string
  source: 'TUSHARE_STK_FACTOR'
  adjustment: 'FORWARD_SNAPSHOT'
  requestedIndicators: Array<'MACD' | 'KDJ' | 'RSI' | 'BOLL'>
  units: {
    close: 'CNY_PER_SHARE'
    macd: 'PRICE'
    kdj: 'PERCENT'
    rsi: 'PERCENT'
    boll: 'CNY_PER_SHARE'
  }
  items: StockTechnicalIndicatorItem[]
}

interface StockTechnicalIndicatorItem {
  tradeDate: string
  close: number | null
  macd: { dif: number | null; dea: number | null; histogram: number | null } | null
  kdj: { k: number | null; d: number | null; j: number | null } | null
  rsi: { rsi6: number | null; rsi12: number | null; rsi24: number | null } | null
  boll: { upper: number | null; middle: number | null; lower: number | null } | null
}
```

输出规则：

- `items` 按 `tradeDate ASC` 返回，最多 500 条。
- 查询时使用 `orderBy tradeDate DESC + take` 命中索引，返回前在内存中反转；禁止数据库无界扫描。
- 未请求的指标组固定返回 `null`，保证输出结构稳定。
- 已请求但该日全部字段为空的指标组仍返回对象，字段为 `null`，并增加 `INDICATOR_FIELDS_PARTIAL` warning。
- `close` 用于核验证据和图表，不代表新增行情来源。

### 4.4 查询流程

`StockTechnicalToolFacade.getIndicators(input)`：

1. 规范化 `tsCode`，校验日期和指标组。
2. 用 `stockBasic.findUnique` 判断证券是否存在；不存在返回 `DATA_NOT_FOUND`。
3. 查询该证券 `StkFactor` 的 `MIN(tradeDate)` 和不晚于请求日的 `MAX(tradeDate)`。
4. 没有任何因子记录返回 `DATA_NOT_READY`。
5. 请求日早于覆盖起点返回 `DATA_NOT_FOUND`，details 携带 `coverageStart`。
6. 按索引读取指定 `lookback` 行，只 select 输出所需字段。
7. 映射稳定 DTO、warnings 和 provenance。

不得复用 `StockAnalysisService.getTechnicalIndicators()` 作为 v1 fallback，因为它是另一套本地计算口径。

### 4.5 Tool Definition

| 字段                 | 值                                     |
| -------------------- | -------------------------------------- |
| key / version        | `get_stock_technical_indicators` / `1` |
| requiredRole         | `USER`                                 |
| sideEffect           | `READ`                                 |
| requiresConfirmation | `false`                                |
| idempotent           | `true`                                 |
| timeoutMs            | `15_000`                               |
| maxAttempts          | `2`                                    |
| maxRows              | `500`                                  |
| costClass            | `MEDIUM`                               |
| resourceClass        | `PUBLIC_MARKET_DATA`                   |

Provenance 固定包含：

```text
sourceType=DATABASE
sourceServices=[StockTechnicalToolFacade]
sourceModels=[StkFactor]
asOf.tradeDate=<dataThrough>
timezone=Asia/Shanghai
currency=CNY
adjustment=FORWARD_SNAPSHOT
dataVersion=stk-factor.v1:<dataThrough>
```

### 4.6 错误映射

| 场景                             | ToolErrorCode      | retryable |
| -------------------------------- | ------------------ | --------- |
| 代码、日期、lookback、指标组非法 | `INVALID_ARGUMENT` | false     |
| 证券不存在或请求日在覆盖起点之前 | `DATA_NOT_FOUND`   | false     |
| 证券存在但技术因子尚未入库       | `DATA_NOT_READY`   | true      |
| 数据库不可用/查询超时            | `UPSTREAM_FAILED`  | true      |
| 结果超过硬上限                   | `RESULT_TOO_LARGE` | false     |

## 5. `get_stock_technical_signals@1`

### 5.1 职责与语义

返回本地确定性引擎计算的标准信号事件、最近发生记录和历史统计。它必须区分：

- `triggeredOnDataThrough=true`：信号在 `dataThrough` 当日刚刚触发。
- `latestOccurrenceDate`：回看窗口内最近一次触发日期。
- 没有触发：明确返回 `false`，不能用结果缺席让模型猜测。
- `direction=BULLISH` 只用于归类，不能描述为保证收益的买入建议。

### 5.2 固定信号目录

v1 只允许当前版本化目录的 14 个 key：

```text
macd.golden-cross
macd.death-cross
kdj.golden-cross
kdj.death-cross
rsi6.oversold-enter
rsi6.overbought-enter
boll.upper-breakout
boll.lower-breakdown
ma.bullish-alignment-enter
ma.bearish-alignment-enter
sar.bullish-state-enter
sar.bearish-state-enter
volume-ratio20.expand-enter
volume-ratio20.shrink-enter
```

每个结果必须携带 `semanticsVersion`、`definitionHash`、方向、表达式参数和证据。算法版本使用现有 `technical-indicator.v2`，来源固定 `LOCAL_QFQ_OHLCV`。

### 5.3 输入 JSON Schema

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["tsCode"],
  "properties": {
    "tsCode": {
      "type": "string",
      "pattern": "^\\d{6}\\.(SH|SZ|BJ)$"
    },
    "asOfDate": {
      "type": "string",
      "format": "date"
    },
    "sections": {
      "type": "array",
      "minItems": 1,
      "maxItems": 3,
      "uniqueItems": true,
      "items": { "enum": ["CURRENT", "OCCURRENCES", "STATISTICS"] },
      "default": ["CURRENT"]
    },
    "signalKeys": {
      "type": "array",
      "minItems": 1,
      "maxItems": 14,
      "uniqueItems": true,
      "items": { "type": "string" }
    },
    "lookbackTradeDays": {
      "type": "integer",
      "minimum": 20,
      "maximum": 1250,
      "default": 60
    },
    "occurrenceLimit": {
      "type": "integer",
      "minimum": 1,
      "maximum": 100,
      "default": 20
    },
    "horizons": {
      "type": "array",
      "minItems": 1,
      "maxItems": 10,
      "uniqueItems": true,
      "items": { "type": "integer", "minimum": 1, "maximum": 60 },
      "default": [1, 3, 5, 10, 20]
    },
    "statisticsPeriod": {
      "enum": ["ONE_YEAR", "THREE_YEARS"],
      "default": "ONE_YEAR"
    },
    "includeBenchmark": {
      "type": "boolean",
      "default": false
    }
  }
}
```

Adapter 额外执行交叉字段校验：

- 未请求 `OCCURRENCES` 时忽略 `occurrenceLimit`，并添加 `UNUSED_INPUT_IGNORED`。
- 未请求 `STATISTICS` 时忽略 `horizons`、`statisticsPeriod`、`includeBenchmark`。
- `includeBenchmark=true` 时基准固定为 `000300.SH`，不接受模型传任意基准。
- `signalKeys` 省略代表全部 14 个；传入未知 key 返回 `INVALID_ARGUMENT`。

### 5.4 输出 `data`

```ts
interface StockTechnicalSignalsData {
  meta: {
    tsCode: string
    name: string | null
    requestedAsOfDate: string | null
    dataThrough: string
    source: 'LOCAL_QFQ_OHLCV'
    adjustment: 'ADJ_FACTOR_RATIO'
    algorithmVersion: 'technical-indicator.v2'
    catalogVersion: string
  }
  current: SectionResult<CurrentSignalResult[]>
  occurrences: SectionResult<SignalOccurrence[]>
  statistics: SectionResult<SignalStatisticsGroup[]>
  buySignalTriggered: boolean
  sellSignalTriggered: boolean
}

type SectionResult<T> =
  | { status: 'OK'; data: T; error: null }
  | { status: 'NOT_REQUESTED'; data: null; error: null }
  | { status: 'ERROR'; data: null; error: { code: string; message: string } }

interface CurrentSignalResult {
  signalKey: string
  displayName: string
  direction: 'BULLISH' | 'BEARISH' | 'CONTEXTUAL'
  semanticsVersion: string
  definitionHash: string
  evaluable: boolean
  notEvaluableReason: string | null
  triggeredOnDataThrough: boolean
  latestOccurrenceDate: string | null
  evidence: Record<string, number | string | null> | null
}
```

输出规则：

- `current` 是核心 section；请求后如果 14 个信号全部不可计算，整个 Tool 返回 `DATA_NOT_READY`。
- `occurrences` 按 `signalDate DESC, signalKey ASC` 稳定排序，最多 100 条，只返回触发证据，不重复携带大体积收益轨迹。
- `statistics` 复用现有 period、horizon、MFE、MAE、置信区间和基准统计 DTO。
- 可选 section 失败时采用 fail-soft：保留成功的 `current`，失败 section 返回 `status=ERROR` 并写 warning；不能把部分失败伪装成全成功。
- `buySignalTriggered` 仅当 `current` 中至少一个 `BULLISH` 信号当日触发；`CONTEXTUAL` 不计入。
- `sellSignalTriggered` 仅当至少一个 `BEARISH` 信号当日触发。

### 5.5 服务重构

新增 `TechnicalSignalEvaluationService`，把“加载点时序列、运行指标引擎、检测 occurrence”的公共流程从 `TechnicalSignalStatisticsService` 中提取：

```ts
interface TechnicalSignalEvaluationQuery {
  tsCode: string
  requestedAsOf?: string
  signalKeys: string[]
  lookbackTradeDays: number
}

interface TechnicalSignalEvaluation {
  dataThrough: string
  catalogVersion: string
  algorithmVersion: string
  current: CurrentSignalResult[]
  occurrences: SignalOccurrence[]
}
```

- `TechnicalSignalStatisticsService` 继续负责统计聚合，但复用 EvaluationService，避免两套信号算法。
- `TechnicalSignalToolFacade` 负责 READY 日期解析、section 编排、fail-soft、输出上限和 Tool 错误映射。
- `TechnicalSignalModule` 提供并导出 `TechnicalSignalToolFacade`；`AgentModule` 只导入该 feature module，不直接注入 Repository。
- 现有 HTTP Controller 的严格 `asOf` 行为保持不变；仅 Agent Facade 把周末或未 READY 日期解析为最近 READY 日期后再调用领域服务。

### 5.6 Tool Definition 与错误

| 字段                 | 值                                  |
| -------------------- | ----------------------------------- |
| key / version        | `get_stock_technical_signals` / `1` |
| requiredRole         | `USER`                              |
| sideEffect           | `READ`                              |
| requiresConfirmation | `false`                             |
| idempotent           | `true`                              |
| timeoutMs            | `30_000`                            |
| maxAttempts          | `2`                                 |
| maxRows              | `1_500`                             |
| costClass            | `HIGH`                              |
| resourceClass        | `PUBLIC_MARKET_DATA`                |

错误映射：

| 领域错误                               | ToolErrorCode      |
| -------------------------------------- | ------------------ |

| 数据共同水位线不存在、全部信号不可计算 | `DATA_NOT_READY`   |

## 6. `get_data_availability@1`

### 6.1 职责

回答“系统有没有这类数据、更新到哪天、为什么查不到”。它读取白名单数据集的水位线、最近同步状态和质量状态，不执行同步，不对大表做每请求全表精确 `COUNT(*)`。

### 6.2 固定数据集目录

v1 支持：

```text
STOCK_DAILY
STOCK_DAILY_BASIC
STOCK_ADJ_FACTOR
STOCK_TECHNICAL_FACTOR
STOCK_MONEYFLOW
FINANCIAL_INDICATOR
INCOME_STATEMENT
BALANCE_SHEET
CASHFLOW
INDEX_DAILY
SECTOR_DAILY
MARKET_MONEYFLOW
HSGT
MARGIN_DETAIL
CYQ_PERF
CYQ_CHIPS
```

每个目录项在源码中固定定义：Prisma Model、日期字段、证券字段、支持 `MARKET`/`SECURITY` 的 scope、质量检查 task、同步 task、允许滞后交易日数、推荐 Tool。禁止把模型传入字符串拼成表名、列名或 Prisma delegate。

### 6.3 输入 Schema

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["datasets"],
  "properties": {
    "datasets": {
      "type": "array",
      "minItems": 1,
      "maxItems": 20,
      "uniqueItems": true,
      "items": { "type": "string" }
    },
    "tsCode": {
      "type": "string",
      "pattern": "^\\d{6}\\.(SH|SZ|BJ)$"
    }
  }
}
```

- `tsCode` 省略：查询市场级水位线。
- `tsCode` 存在：只允许目录中支持 `SECURITY` 的数据集；不支持的组合返回 `INVALID_ARGUMENT`。
- 未知 dataset key 返回 `INVALID_ARGUMENT`，不能降级为任意数据库查询。

### 6.4 输出与状态规则

```ts
interface DataAvailabilityItem {
  dataset: string
  scope: 'MARKET' | 'SECURITY'
  tsCode: string | null
  status: 'READY' | 'DEGRADED' | 'EMPTY' | 'FAILED'
  coverageStart: string | null
  dataThrough: string | null
  rowCount: number | null
  lastSyncedAt: string | null
  syncStatus: 'SUCCESS' | 'FAILED' | 'RUNNING' | 'UNKNOWN'
  qualityStatus: 'PASS' | 'WARN' | 'FAIL' | 'UNKNOWN'
  lagTradingDays: number | null
  recommendedTool: string | null
  notes: string[]
}
```

状态优先级：

1. 无任何水位线：`EMPTY`。
2. 最近同步失败或最近质量检查 FAIL：`FAILED`。
3. 质量 WARN，或滞后超过该目录项阈值：`DEGRADED`。
4. 有水位线且没有 FAIL/WARN/超阈值：`READY`；质量记录缺失时 `qualityStatus=UNKNOWN` 并附 note，不阻止读取已有数据。

性能规则：

- 市场级大表 `rowCount=null`，不执行全表精确计数。
- 单证券 scope 可用索引执行 count，但需要设置 statement timeout；超时则 `rowCount=null` 和 warning，不影响水位线。
- `MIN/MAX` 必须命中固定日期/证券索引。实现前对 16 个 resolver 执行 `EXPLAIN (ANALYZE, BUFFERS)`。
- 同一请求最多 20 个数据集，Repository 内允许有界并发 4，禁止无界 `Promise.all`。

### 6.5 模块边界与 Tool Definition

新增独立 `DataAvailabilityModule`：

```text
DataAvailabilityModule
  -> DataAvailabilityRepository
  -> DataAvailabilityCatalog
  -> DataAvailabilityToolFacade
```

该模块只读，不复用带修复/重跑副作用的管理端数据质量 Service。`AgentModule` 导入模块并注入 Facade。

| 字段                 | 值                            |
| -------------------- | ----------------------------- |
| key / version        | `get_data_availability` / `1` |
| requiredRole         | `USER`                        |
| sideEffect           | `READ`                        |
| requiresConfirmation | `false`                       |
| idempotent           | `true`                        |
| timeoutMs            | `10_000`                      |
| maxAttempts          | `2`                           |
| maxRows              | `20`                          |
| costClass            | `LOW`                         |
| resourceClass        | `PUBLIC_MARKET_DATA`          |

Planner 只在用户明确询问覆盖/更新时间，或业务 Tool 返回 `DATA_NOT_READY`/`DATA_NOT_FOUND` 后需要解释时调用；禁止每个研究请求都先调用一次。

## 7. `screen_stocks@2`

### 7.1 为什么必须升版本

现有选股 SQL 的 5 个条件是筛选启发式，不等于标准信号目录：

| v1 名称/表现 | 实际条件                            | v2 稳定 key                              |
| ------------ | ----------------------------------- | ---------------------------------------- |
| MACD 金叉    | 当日 DIF 上穿 DEA                   | `MACD_GOLDEN_CROSS`                      |
| KDJ 金叉     | 当日 K 上穿 D                       | `KDJ_GOLDEN_CROSS`                       |
| “MA 多头”    | `close > boll_mid AND macd_dif > 0` | `MACD_POSITIVE_AND_CLOSE_ABOVE_BOLL_MID` |
| “BOLL 超卖”  | `close < boll_lower`                | `CLOSE_BELOW_BOLL_LOWER`                 |
| “RSI 超卖”   | `rsi6 < 20` 的状态                  | `RSI6_BELOW_20`                          |

后三项不能映射为 `ma.bullish-alignment-enter`、`boll.lower-breakdown`、`rsi6.oversold-enter`。v2 必须使用诚实命名，输出称为 `screeningHeuristics`，不笼统称为“买入信号”。

### 7.2 v2 变更

- v1 Definition、输入输出和历史调用保持原样。
- v2 在现有输入上新增 `tsCodes?: string[]`，1–20 个、去重、证券代码格式校验。
- `StockScreenerService` 在 SQL 层增加 `sb.ts_code = ANY($n::text[])`，不能先查全市场再在 Adapter 过滤。
- v2 输出新增：

```ts
heuristicCatalogVersion: 'stock-screener-heuristics.v1'
screeningHeuristicCount: number
screeningHeuristics: Array<{
  key: string
  displayName: string
  matched: boolean
  evidence: Record<string, number | null>
}>
```

- 稳定排序固定为 `screeningHeuristicCount DESC, pctChg DESC, tsCode ASC`；分页结果不得因同分随机漂移。
- 精确回答“某股票今天有没有标准信号”调用 `get_stock_technical_signals`；回答“全市场哪些股票启发式条件最多”才调用 `screen_stocks@2`。

### 7.3 v2 Policy

沿用 v1 的公共只读 Policy、超时和行数限制；版本固定为 2。Registry 同时注册 v1 和 v2，规划阶段暴露最新启用版本，历史计划按 pin 继续执行 v1。

## 8. Workflow v5 与 Tool 版本支持

### 8.1 当前阻塞

`screen_stocks@2` 不能直接加入当前规划器：

- `RESEARCH_PLAN_SCHEMA` 把 `toolVersion` 写死为 `const: 1`。
- `ResearchPlanCompilerService.assertToolCall` 强制版本必须为 1。
- `PlanNode` 直接 import v1 的 plan schema，没有从冻结 Workflow Definition 读取 schema。

### 8.2 改造方案

1. `WorkflowDefinition` 新增只读字段 `planSchema: Record<string, unknown>`。
2. v1–v4 的 `planSchema` 继续指向当前 `RESEARCH_PLAN_SCHEMA_V1`，定义和 hash 保持不变。
3. 新增 `RESEARCH_PLAN_SCHEMA_V2`，`toolVersion` 改为正整数，实际是否存在由冻结的 Tool Registry snapshot 校验。
4. `PlanNode` 使用 `state.workflow.planSchema`，禁止直接 import v1 schema。
5. Compiler 只校验 `toolVersion` 是正整数；`ToolRegistryService.resolve(key, version)` 负责拒绝不存在或未启用的 pin。
6. 新增 `STOCK_RESEARCH_WORKFLOW_V5`，使用 plan schema v2，allowlist 加入三个新 Tool key，当前版本切到 v5。
7. v5 Planner Prompt 加入明确路由样例和反例。

路由最小规则：

| 用户意图                       | Tool                                  |
| ------------------------------ | ------------------------------------- |
| 单股 MACD/KDJ/RSI/BOLL 数值    | `get_stock_technical_indicators@1`    |

## 9. `stk_factor` 同步限流加固

这是上线新 Tool 前的 P0.0 前置项。它不改变 Agent 查询路径，但防止全量回补触发 Tushare 上限。

### 9.1 配置

在 `TushareConfig` 和 `.env.example` 增加：

```dotenv
# stk_factor 5000 积分档官方上限 100 次/分钟；650ms 约 92 次/分钟，留安全余量
TUSHARE_STK_FACTOR_MIN_INTERVAL_MS=650
```

配置规则：

- 默认 650 ms，不依赖部署账号一定有 8000+ 积分。
- 允许高积分账号显式调低，但必须大于等于 120 ms。
- 配置非法时启动失败，不使用 `||` 静默回退错误值。
- 保留 `TUSHARE_RATE_LIMIT_RETRY_DELAY_MS=65000` 和 `40203` 重试作为二级保护。
- 不复用当前全局 `TUSHARE_REQUEST_INTERVAL_MS`，因为不同 API 的官方频率不同。

### 9.2 Client 改造

`TushareClient` 构造时创建实例级 `rateLimitIntervals`：

```ts
this.rateLimitIntervals = new Map([
  ...DOCUMENTED_RATE_LIMIT_MS,
  [TushareApiName.STK_FACTOR, cfg.stkFactorMinIntervalMs],
])
```

`waitForRequestSlot()` 从实例 map 读取。保留同 API 串行队列和全局并发 5。连续两个 `stk_factor` 请求的开始时间差必须 `>= configured interval`。

### 9.3 全量回补断点和失败策略

复用现有 `TushareSyncProgress` 与 `SyncHelperService`：

1. full 模式开始时读取 `getResumeKey(STK_FACTOR)`；存在 RUNNING 断点时从下一开放交易日继续。
2. 没有断点时 `markRunning(STK_FACTOR, totalDates)`。
3. 每个日期事务成功后调用 `updateProgress(STK_FACTOR, tradeDate, completed, total)`。
4. 某日期失败后不得越过该日期推进安全断点；写入 retry queue，并停止本次 `stk_factor` full 任务，避免最终日志显示 SUCCESS 但历史有洞。
5. 全部完成后 `markCompleted(STK_FACTOR)`。
6. 增量模式仍可记录失败日期，但最终状态必须为 FAILED/PARTIAL，而不是无条件 SUCCESS。

不得由 Agent Tool、Planner 或普通查询 API 触发 full sync。full sync 只能通过现有管理入口/任务计划执行，并保留审计。

### 9.4 上游字段契约修复

同步改造同时处理字段错配：

- 对照官方响应审计 `TUSHARE_STK_FACTOR_FIELDS`。
- v1 Tool 不读取 `cci_14`、`cci_20`、`tr`、`atr14`、`atr20`、`vr_26`。
- Mapper 对官方未返回字段不得默认为 0。
- 新增数据质量检查：每日有效行中 MACD/KDJ/RSI/BOLL 各组非空比例低于阈值时标记 WARN/FAIL。
- 是否新增官方 `cci` 列单独立项；未完成 migration、回补和质量验收前，不加入 Tool enum。

## 11. 测试计划

### 11.1 指标 Tool

1. 非法证券代码、日期、指标组、lookback 被 Schema 拒绝。
2. 股票不存在返回 `DATA_NOT_FOUND`。
3. 股票存在但无 `StkFactor` 返回 `DATA_NOT_READY`。
4. 周末、节假日、盘中请求解析到最近 READY 日并返回 warning。
5. `lookback=500` 只查询 500 行，输出升序。
6. 未请求指标组为 null；请求组字段准确映射。

8. Facade 与 Adapter 依赖图中不存在 `TushareClient`/`FactorDataApiService`。

### 11.2 信号 Tool

1. 用手工可验证的小型 OHLCV 序列测试 MACD/KDJ 交叉，不只做快照测试。
2. 无当日触发时明确返回 `triggeredOnDataThrough=false`。

6. `STATISTICS` 或 benchmark 失败不抹掉成功的 CURRENT section。
7. occurrence 排序和 100 条上限稳定。

### 11.3 可用性 Tool

1. 构造 READY、DEGRADED、EMPTY、FAILED 四态。
2. 市场 scope 和证券 scope 水位线正确。
3. 不支持证券 scope 的 dataset 组合返回 `INVALID_ARGUMENT`。

1. `tsCodes` 在 SQL 层生效，结果只含请求证券。

1. fake timer 验证连续 `stk_factor` 请求间隔 `>=650ms`。

### 15.2 真实 PostgreSQL 与性能证据

真实库抽取 30 只上市股票，覆盖沪市 11、深市 10、北交所 9，其中包含 `600089.SH`：

| 验收项                   | 结果                            |
