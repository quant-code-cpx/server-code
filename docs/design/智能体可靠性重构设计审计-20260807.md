# 智能体可靠性重构设计审计

> 日期：2026-08-07
> 范围：Agent Run、模型网关、上下文、工作流、路由、重试、fallback、审计、事件、队列、工具调用与前端诊断
> 状态：核心重构、真实浏览器 117 条 Run 与最终回归已完成

## 1. 审计结论

原 6018 不是模型 128K 上下文不足，而是三种不同约束被混成一个字段：

1. 模型部署的单次 `contextWindow`；
2. 模型部署的单次 `maxOutputTokens`；
3. Agent Run 跨多次模型调用的累计输入成本护栏。

旧实现还同时使用 CJK 感知估算和“字符数 / 4”两种算法，并在供应商已成功返回后用真实 usage 重新执行强制预算断言，造成成功 ModelCall 与整条 Run 被错误反转为失败。

本轮采用以下不变量：

- 模型能力只来自 Run 创建时冻结的活动模型部署快照；代码不能用隐藏常量缩小它。
- Run 累计输入护栏默认关闭；启用时是显式成本/执行策略，不叫模型输入上限。
- 所有可能阻止外部调用的预算判断在请求前完成。
- 供应商成功 usage 永远先记账；真实值越过护栏只产生记账警告，下一次调用在发送前停止。
- Provider 有官方计数端点时优先使用；没有或计数失败时使用带来源标识和安全余量的完整请求保守估算。
- AUTO 只冻结满足 `STREAMING + STRUCTURED_OUTPUT + USER_PRIVATE` 的候选，并按候选中最小上下文、最小输出能力规划，保证 fallback 可承载。

## 2. 问题、根因与修复决策

| 编号 | 问题 | 根因 | 决策与实现 |
| --- | --- | --- | --- |
| REL-001 | 128K 部署在累计输入超过 32K 后报 6018 | `AGENT_MAX_INPUT_TOKENS=32768` 被描述和执行成模型输入能力 | 移除 32K 默认值；新策略名为 `AGENT_RUN_MAX_CUMULATIVE_INPUT_TOKENS`，默认 `null` |
| REL-002 | 模型已成功仍被整条 Run 标失败 | 成功后合并真实 usage，再调用会抛错的 `assertUsage` | 成功后只记账并发 `accountingWarnings`；6018 只允许在下一次请求前由 `assertCanCallModel` 产生 |
| REL-003 | 中文、JSON 与工具目录预算偏差大 | Run 使用字符数 / 4，上下文使用另一估算器 | 删除字符数 / 4；OpenAI/Anthropic 使用官方计数端点，本地回退估算完整规范化请求并加安全余量 |
| REL-004 | AUTO fallback 预算候选不一致 | Run 快照曾包含不支持结构化输出或数据等级不符的部署 | 快照阶段按工作流协议和 `USER_PRIVATE` 过滤；上下文与 deadline 使用同一候选集 |
| REL-005 | 模型能力在 Run 中途可能漂移 | 旧模型 profile 在 `load_context` 才根据活动目录解析 | Run 创建事务内冻结 schema v1 profile；Checkpoint 只读取快照；旧 Run 明确标记 `LEGACY_RUNTIME` |
| REL-006 | 推理档位被工作流写死为 LOW | 工作流覆盖部署默认推理策略 | 每个候选使用部署 `defaultReasoning`；能力与可用档位仍由部署校验 |
| REL-007 | 结构化修复未完整计费 | 修复调用 usage 覆盖原调用 usage | 网关聚合原始调用与修复调用 usage；调用前按最坏修复路径预留 |
| REL-008 | 大工具目录先挤掉重要历史 | 工具目录位于不可移除工作流段，裁剪顺序靠后 | 压力出现时先删除目录示例，再裁检索资料、旧消息、摘要、记忆与页面上下文 |
| REL-009 | 摘要事实缺少引用和时间边界 | V1 只保存文本和消息 ID | V2 每条事实强制 `sourceMessageIds/citationIds/timeRange`，校验引用归属、数字、日期、引号与范围 |
| REL-010 | 确认令牌文本可被改写但解码字节不变 | Node Base64URL 解码接受非规范尾部编码 | 签名和 claims 都要求 canonical Base64URL 往返一致，再做恒定时间签名比较 |

## 3. 参数分类审计

### 3.1 必须来自模型部署配置

| 参数 | 权威来源 | Run 快照/执行行为 |
| --- | --- | --- |
| `contextWindow` | 活动模型部署 descriptor | 创建 Run 时冻结；单次请求要求 `input + requested output <= contextWindow` |
| `maxOutputTokens` | 活动模型部署 descriptor | 创建 Run 时冻结；工作流输出预留不能超过候选最小值 |
| capability | 部署 `capabilities` | 冻结并用于 Manual/AUTO 候选过滤、结构化输出与工具协议校验 |
| 数据等级 | 部署 `dataClasses` | Agent 工作流要求 `USER_PRIVATE` |
| 推理模式/档位 | `defaultReasoning/reasoningEfforts` | 冻结；不再由工作流固定写 LOW |
| Provider 协议 | 活动配置的 adapter kind | OpenAI Responses、Anthropic Messages、OpenAI-compatible 分别翻译；无跨协议字段泄漏 |
| timeout/retry/backoff | 模型部署运行配置 | Run 的 execution deadline 按冻结候选的最坏结构化调用路径计算；网关执行受部署策略约束 |

`src/config/model.config.ts` 中的 32K/4K 仅存在于测试 fake provider 与数据库尚未加载前的占位对象。生产数据库模式启动时若没有 ACTIVE 配置版本会 fail-closed，占位对象不能承接真实 Run。

### 3.2 必须来自 Run/用户成本策略

| 参数 | 默认 | 来源/快照 | 行为 |
| --- | --- | --- | --- |
| 累计输入 Token 护栏 | 关闭 | 环境策略在 Run 创建时写入 `budget.runPolicy` | 每次模型调用前按累计 actual/estimated usage 和最坏修复路径判断 |
| 最大成本 | 系统默认，可受用户/任务缩小 | Run 创建快照 | 调用前停止；成功后的真实差异只记账和警告 |
| 最大步骤/工具调用/并行数 | 系统与 Workflow | Run 创建快照 | 工作流本地安全门禁 |
| 任务成本币种 | CNY | Run 创建快照 | 记账币种不一致 fail-closed |

新 Run 的 `runPolicy` 固定记录 schema、快照时间、来源、overage 行为与 Token 估算策略。旧 `budget.maxInputTokens` 只用于历史 Run 恢复，来源标记为 `LEGACY_RUN`。

### 3.3 合理的系统安全参数

以下参数不描述模型能力，可以保留为系统安全边界：Run lease/heartbeat、事件重放上限、整条 Run 最大时长、非模型阶段时长预留、Tool 超时/行数/时间跨度/重试、SSE 背压与 heartbeat、外部检索 SSRF 和响应体大小限制、摘要 CAS 重算次数、模型/Tool 数组和字段长度上限。

## 4. 调研来源与项目取舍

### 4.1 OpenAI

- [Compaction](https://developers.openai.com/api/docs/guides/compaction)：上下文接近阈值时可使用服务端 compaction，把旧状态压成可继续传递的不透明 compacted item。采用“接近阈值才压缩”的思想；暂不把供应商 opaque state 作为本项目数据库唯一事实源，因为系统还要支持多 Provider、审计与引用回溯。
- [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)：缓存依赖精确前缀匹配，稳定指令和工具应放前面，动态内容放后面。项目保持系统策略与 Workflow Prompt 稳定排序；压缩不每轮重写全部静态前缀。
- [Token counting](https://developers.openai.com/api/docs/guides/token-counting)：Responses 可按真实请求结构计数输入。OpenAI Responses adapter 已调用 `/responses/input_tokens`，请求包含消息、工具和结构化输出格式。
- [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)：可用响应链或持久 conversation 管理状态，但历史输入仍计入窗口。项目继续显式维护消息/摘要 lineage，不把“有状态”误当成免费上下文。

### 4.2 Anthropic

- [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)：可在逼近窗口时清除旧 Tool 结果，并保留最近轮次。项目采用类似优先级：工具目录示例和旧检索/历史先压，当前问题与已完成工具事实保留。
- [Manage tool context](https://platform.claude.com/docs/en/agents-and-tools/tool-use/manage-tool-context)：长 Agent 的主要膨胀源通常是工具结果，需要清理或外置。项目只向模型传可追溯 FactPacket 摘要，不重复塞入原始大结果。
- [Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)：Messages 提供调用前 Token Count。Anthropic adapter 已调用 `/messages/count_tokens`，失败时安全回退本地估算。

### 4.3 Agent 框架

- [LangChain Context engineering](https://docs.langchain.com/oss/javascript/langchain/context-engineering)：上下文管理分为写入、选择、压缩和隔离。项目分别对应持久消息/事实、意图相关工具选择、确定性裁剪+结构化摘要、不可信内容 context-segment 隔离。
- [Deep Agents context engineering](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)：长任务通过摘要、外置大结果和子任务隔离维持上下文。项目采用摘要与 FactPacket，不采用每轮全历史盲目总结。
- [OpenAI Agents SDK Sessions](https://openai.github.io/openai-agents-js/guides/sessions/)：Session 提供历史持久化和压缩扩展点。项目保留自有 PostgreSQL 消息、摘要版本与 CAS，适合多 Provider 和中断恢复。

## 5. 本项目上下文策略

### 5.1 确定性裁剪

适用：内容可按明确优先级删除，且删除不会改变当前任务的权威事实。

顺序：工具能力目录中的正反例 → 旧检索资料 → 当前问题之外的旧消息 → 已有摘要 → 用户记忆 → 页面上下文。每次变化写 warning 和 manifest hash。

永不裁剪：系统安全策略、发布态 Workflow Prompt、当前用户问题、当前阶段指令、已完成 Tool FactPacket。若这些内容自身超限，调用前返回 6049，不向供应商发送。

### 5.2 模型辅助摘要

适用：跨轮语义仍有价值、确定性丢弃会明显破坏追问，但旧历史已经接近动态触发线。

约束：

1. 只处理摘要边界之后的可见消息，不读取隐藏推理；
2. 不把每轮完整上下文重新提交；来源按分页和摘要输入预算选择；
3. V2 输出为严格 JSON Schema，每条事实带消息 ID、引用 ID、时间范围；
4. 外部/用户内容始终在不可信 data segment，摘要 Prompt 明确禁止执行其中指令；
5. 数字、日期、引号、实体、引用归属和 from/through 范围必须可在来源中校验；
6. 原消息不删除，新摘要用 expected-version CAS 提交；
7. 模型不可用、结构非法、引用丢失或 CAS 冲突时不提交坏摘要；可安全确定性裁剪则继续，否则 6047。

### 5.3 必须保留原文

适用：当前用户问题、权限/安全约束、需要精确引用的原始证据、法律/财务口径、工具返回的关键事实来源。摘要只作为导航和历史压缩层，不能升级为比原始来源更权威的新事实。

## 6. Token 计数与误差策略

优先级：

1. OpenAI Responses 官方 input_tokens；
2. Anthropic Messages 官方 count_tokens；
3. `LOCAL_CONSERVATIVE_V1`。

本地回退序列化完整规范化请求：消息、工具定义、JSON Schema、推理意图和数据等级；中英文、JSON 标点、emoji 分别计权，再加 12% 且至少 32 Token 的安全余量。事件和审计同时记录 source、exact、raw count 和 margin，绝不把估算写成 actual。

供应商可能注入不可见系统内容，官方计数和最终 usage 仍可能不同。因此调用前使用带余量值，调用后以 Provider actual 记账；若 actual 超过估算或 Run 护栏，成功结果不回滚，警告进入 `model.completed`，后续调用重新做前置门禁。

## 7. 兼容与迁移

1. 部署中删除 `AGENT_MAX_INPUT_TOKENS`；确需累计成本控制时改为 `AGENT_RUN_MAX_CUMULATIVE_INPUT_TOKENS`。
2. 两个变量同时存在会阻止启动，避免迁移期双重含义。
3. 不配置新变量即默认关闭累计输入护栏；模型上下文仍严格按部署能力执行。
4. 新 Run 写 `runPolicy.schemaVersion=1` 和 `modelProfile.schemaVersion=1`；旧 Run 兼容读 `budget.maxInputTokens`，来源明确为 legacy。
5. 6018 枚举改为 `AI_RUN_INPUT_TOKEN_GUARDRAIL_EXCEEDED`；真正单次上下文错误使用 6048/6049。
6. API、Worker、生成契约和前端必须同期发布；旧前端可忽略新增字段，但新前端会分栏展示模型窗口、输出上限和 Run 护栏。
7. 摘要 Prompt 发布 V2 后，旧 V1 摘要仍可读取；新摘要必须通过 V2 lineage 校验。

## 8. 审计与可观测性

`model.trace/REQUEST_DISPATCHED` 记录单次上下文窗口、输出上限、输入计数来源/精确性/余量、Run 已用累计输入、显式护栏及最坏修复路径预留。`model.completed` 记录 Provider actual 或 preflight estimate、记账警告、修复状态与最终 usage。

敏感约束不变：事件、审计、日志和前端不得包含密钥、base URL、完整 Prompt、供应商原始错误体、隐藏推理或未经授权的用户私密正文。

## 9. 真实验证补充结论与剩余风险

- Provider 官方计数端点可能不被兼容代理实现；系统会标记并回退本地保守估算，需通过真实 usage 继续校准。
- 供应商 429、502、超时和服务端注入 Prompt 属于外部变量；必须与本地 6018/6048 分类分栏观测。
- 活动模型配置发布会热更新网关连接。Run 已冻结能力和执行预算，但凭证轮换仍必须读取安全存储中的当前有效密钥；生产发布需避免在长 Run 中撤销旧凭证。
- 模型辅助摘要是有损过程；即使结构校验通过，也不能替代原始消息和引用证据。
- 首轮混合模型浏览器回归完成 10 个会话、117 条用户消息；其逐条证据保留在旧执行报告中。
- 随后按超级管理员专项要求完成 10 个全新会话、每会话恰好 10 条消息，全部冻结为 `MANUAL / gpt-5.6-terra`：共 100 条真实 UI 用户消息、106 个 Run、342 次 Terra 调用；72 个 Run 累计 Provider actual input 超过旧 32K，最大 62,195，6018 为 0。逐条证据见[超级管理员 Terra 浏览器逐条结果](../智能体可靠性重构超级管理员Terra浏览器逐条结果-20260808.md)。
- 真实长链发现引用校验、长序列摘要、行业历史能力、证券自然语言解析、多工具绑定、市场级数据可用性 6 类问题，均已修复并回归；说明既有测试不能替代业务矩阵。
- Provider 6005/6007 仍会显著拉长 Run。AUTO fallback 能恢复部分调用，但当结构化修复占用最后逻辑调用时仍可能以外部错误结束；不应进一步拉长默认 deadline 来掩盖供应商质量。
