# 个股技术信号统计后端设计

> 状态：🔧 待实现 · 文档版本：v1.0 · 编制日期：2026-08-03
>
> 适用范围：NestJS 后端、Prisma/PostgreSQL、Redis、Tushare 日线/复权因子/技术因子数据
>
> 关联设计：[条件订阅规则引擎-后端设计](./条件订阅规则引擎-后端设计.md)

## 1. 结论与实施决策

当前系统**没有**完整的“个股技术信号历史绩效统计”能力。已有技术指标、择时信号、策略信号历史、事件研究和次日表现统计等零散能力，但尚不能可靠回答以下问题：

- 某只股票近一年、近三年出现过多少次 MACD 金叉等技术信号；
- 信号后第 1、3、5、10、20 个市场交易日上涨、下跌、平盘各占多少；
- 后续收益的平均值、中位数、最大值、最小值、标准差分别是多少；
- 空头信号判断正确的比例是多少；
- 每一个统计样本来自哪一天、使用了什么信号证据、为何被纳入或排除；
- 数据更新或算法升级后，历史结果能否按原口径复现。

本方案把需求中的 `mcdn` 按常见指标 **MACD** 处理；若确指另一个指标，只需新增 Metric Catalog 定义，不改变统计框架。

采用以下落地决策：

1. 新建独立的 `technical-signal` 领域模块，统一信号语义、样本生成、收益计算与统计，避免继续扩张 `StockAnalysisService`。
2. P0 先做单股、按需计算，不新增统计结果表。单股三年约 750 个交易日，现有复合索引足以支撑；Redis 仅做可失效缓存。
3. 技术信号一律定义为“状态转换事件”，不把连续多日处于超买/超卖状态重复计数。
4. 后续收益使用 `Daily + AdjFactor` 计算复权收益，不能使用当前实际为空的 `StkFactor.pctChg`，也不能直接用未复权收盘价。
5. T+N 指交易所第 N 个开市日。股票停牌导致目标日无行情时记为缺失样本，不能顺延到该股票下一条行情。
6. 统计摘要与样本明细分开提供；摘要不分页后聚合，明细可分页并可审计复算。
7. 信号定义与既有《条件订阅规则引擎》共用 `TechnicalSignalDefinitionService` 和版本号，后续订阅、选股、个股详情不再各自维护口径。
8. P2 全市场扫描才复用计划中的 `TechnicalSignalDailySnapshot` / `TechnicalSignalEvent` 持久化模型；P0 不建立第二套重复事件表。

## 2. 需求边界

### 2.1 P0 必须交付

- 单只 A 股的近 1 年、近 3 年及自定义日期区间统计；
- MACD、KDJ、RSI6、BOLL 首批 8 类事件；
- T+1/T+3/T+5/T+10/T+20，可由请求指定 1～60；
- 信号发生次数、可到期数、有效数、未到期数、缺失数及缺失原因；
- 原始上涨/下跌/平盘比例和方向性成功率；
- 平均值、中位数、最大值、最小值、样本标准差、P25、P75；
- 信号样本明细、触发前后证据、目标交易日与收益；
- 数据截止日、信号语义版本、统计版本、收益口径版本；
- 严格的数据就绪校验、Redis 缓存、Swagger 契约、自动化测试与压力验收。

### 2.2 P0 不做

- 不做自动下单、资金曲线、仓位管理和手续费模拟；这些属于回测/交易域。
- 不把技术信号统计解释为投资建议或未来收益预测。
- 不做全市场所有股票的每日离线预计算和排行榜。
- 不做盘中分钟级信号；数据粒度固定为日线。
- 不在 P0 持久化派生统计结果，避免算法迭代后产生数据迁移负担。
- 不把“区间内最大/最小单次收益”混同为 MFE/MAE。路径内最大有利/不利波动放在 P1。

### 2.3 P1/P2 扩展

| 阶段 | 能力                                                          | 前置条件                           |
| ---- | ------------------------------------------------------------- | ---------------------------------- |
| P1   | 基准超额收益、MFE/MAE、置信区间、MA/SAR/量价事件、CSV 导出    | P0 语义与收益口径冻结              |
| P2   | 全市场历史回填、每日事件持久化、信号排行榜、订阅 SIGNAL_EVENT | 条件订阅 B3 模型落地、容量测试通过 |
| P3   | 参数化研究、横截面分组、显著性检验、多信号组合                | 防止数据窥探与多重检验方案评审通过 |

### 3.4 已确认的语义冲突

1. RSI：择时模块以 RSI6 从 `<20` 回升至 `>=20` 为买入；选股模块把当日 `<20` 状态直接算作买入。
2. BOLL：跌破下轨在择时模块是 warning，在选股模块被计为买入条件。
3. `MA_BULLISH` 实际判断 `close > boll_mid && macd_dif > 0`，并非均线多头排列。
4. MACD/KDJ 穿越逻辑散落在分析、择时和选股路径，没有统一 `signalKey + parameters + semanticsVersion`。
5. `/technical` 使用本地复权后计算，`/factors/latest` 使用 Tushare 预计算，两条路径没有数据源或算法版本标识。
6. 部分代码把 `DIF == 0` 直接归入“零轴下”，边界定义不严谨。

在统一服务上线前，旧接口只能标记为 legacy，不能宣称与新统计完全同口径。

## 4. 领域定义与统计口径

### 4.1 统一术语

| 术语                   | 定义                                                          |
| ---------------------- | ------------------------------------------------------------- |
| `dataAsOf`             | 因子、日线、复权因子和交易日历共同达到 READY 的最后市场交易日 |
| 信号事件               | 指标从非触发状态跨入触发状态的唯一日期，不是持续状态          |
| `occurrenceCount`      | 信号日期落在统计窗口内的事件总数                              |
| `eligibleOutcomeCount` | 目标 T+N 已不晚于 dataAsOf 的事件数                           |
| `validOutcomeCount`    | 到期且入场价、出场价、复权因子均完整的事件数                  |
| `immatureCount`        | 目标 T+N 晚于 dataAsOf、尚未到期的事件数                      |
| `missingCount`         | 已到期但因停牌或数据缺失无法计算的事件数                      |
| 原始收益               | 不考虑信号方向的股票复权收益                                  |
| 方向性收益             | 多头等于原始收益，空头等于原始收益取反                        |

必须满足：

`occurrenceCount = eligibleOutcomeCount + immatureCount`

`eligibleOutcomeCount = validOutcomeCount + missingCount`

所有收益统计、涨跌比例和成功率的分母均为 `validOutcomeCount`，绝不把 null 当 0。

### 4.2 首批信号目录

首批定义与《条件订阅规则引擎》已冻结方向保持一致。阈值属于语义版本的一部分，不能静默修改。

| signalKey               | 版本      | 方向    | 严格触发条件（prev → curr）                           | 最小证据                |
| ----------------------- | --------- | ------- | ----------------------------------------------------- | ----------------------- |
| `macd.golden-cross`     | `macd.v1` | BULLISH | `prev.dif <= prev.dea && curr.dif > curr.dea`         | prev/curr DIF、DEA      |
| `macd.death-cross`      | `macd.v1` | BEARISH | `prev.dif >= prev.dea && curr.dif < curr.dea`         | prev/curr DIF、DEA      |
| `kdj.golden-cross`      | `kdj.v1`  | BULLISH | `prev.k <= prev.d && curr.k > curr.d`                 | prev/curr K、D、J       |
| `kdj.death-cross`       | `kdj.v1`  | BEARISH | `prev.k >= prev.d && curr.k < curr.d`                 | prev/curr K、D、J       |
| `rsi6.oversold-enter`   | `rsi6.v1` | BULLISH | `prev.rsi6 >= 30 && curr.rsi6 < 30`                   | prev/curr RSI6、阈值 30 |
| `rsi6.overbought-enter` | `rsi6.v1` | BEARISH | `prev.rsi6 <= 70 && curr.rsi6 > 70`                   | prev/curr RSI6、阈值 70 |
| `boll.upper-breakout`   | `boll.v1` | BULLISH | `prev.close <= prev.upper && curr.close > curr.upper` | prev/curr close、upper  |
| `boll.lower-breakdown`  | `boll.v1` | BEARISH | `prev.close >= prev.lower && curr.close < curr.lower` | prev/curr close、lower  |

规则约束：

- 任何必需字段为 null 时当日结果为 `NOT_EVALUABLE`，不产生事件；
- 相等只属于穿越前一侧，穿越日必须严格大于/小于，避免边界重复；
- 检测窗口必须额外加载开始日前一条因子记录，但仅统计信号日位于窗口内的事件；
- 不允许同一 `signalKey + semanticsVersion + tsCode + signalDate` 重复；
- `source = TUSHARE_STK_FACTOR` 固定写入元数据；未来增加本地计算源时必须使用不同 source 和版本，不能混合聚合；
- RSI v1 的 30/70 与旧路径的 20/80、回升触发不同。旧接口保留 legacy 标签，迁移后才切换。

### 4.3 时间窗口

- 所有日期以 `Asia/Shanghai` 解释并序列化为 `YYYYMMDD`，数据库继续使用 `DATE`；
- 未传 `asOfTradeDate` 时，解析为四类依赖数据的最后共同 READY 交易日；
- 显式传入日期时，该日必须是开市日且数据 READY，不允许悄悄回退；
- `1Y`：从 `dataAsOf` 向前减一个公历年，取不早于该日期的第一个开市日；
- `3Y`：同理向前减三个公历年；
- 自定义窗口必须 `startDate <= endDate <= dataAsOf`，跨度 P0 不超过 10 年；
- 闰年使用日历运算，不用固定 365/1095 天替代。

### 4.4 T+N 与停牌

`T+N` 是信号日 T 之后，`exchange_trade_calendars` 中 SSE 的第 N 个 `is_open='1'` 日期。深市、北交所当前日历与 SSE 共用 A 股开市日；如果将来出现差异，按证券交易所路由。

目标市场日存在、但该股票因停牌没有日线时：

- 不把股票恢复交易后的第一条行情当作 T+N；
- `qualityStatus = MISSING_QUOTE`；
- 进入 `missingCount`，不进入收益分母；
- 明细保留预期目标日和缺失原因。

### 4.5 复权收益

P0 支持两种入场口径：

```text
SIGNAL_CLOSE（默认）
R(T, h) = [close(T+h) × AF(T+h)] / [close(T) × AF(T)] - 1

NEXT_OPEN
R(T, h) = [close(T+h) × AF(T+h)] / [open(T+1) × AF(T+1)] - 1
```

其中 `AF` 为 `AdjFactor.adjFactor`。前复权价格还包含共同锚点因子，但在收益率比值中抵消，因此上述比值与同一锚点的前复权收益一致。

约束：

- `NEXT_OPEN` 的 h=1 表示 T+1 开盘入场、T+1 收盘退出；
- 任一价格非有限数、价格 `<= 0` 或复权因子缺失/`<= 0`，该 horizon 记为缺失；
- 不使用 `StkFactor.pctChg`；不使用未经复权的 `Daily.close` 比值；
- 内部使用未舍入 double 计算，API 输出百分比统一保留 6 位小数；
- 平盘判定使用收益率绝对值 `<= 1e-8`，展示舍入不能改变分类；
- 未来支持基准时，基准必须使用相同日期、入场口径和复权策略，`excessReturn = stockReturn - benchmarkReturn`。

### 4.6 统计量

对每个 `period × signalKey × horizon` 独立统计：

```text
upCount       = count(rawReturn >  epsilon)
downCount     = count(rawReturn < -epsilon)
flatCount     = count(abs(rawReturn) <= epsilon)
upRatio       = upCount / validOutcomeCount
downRatio     = downCount / validOutcomeCount
flatRatio     = flatCount / validOutcomeCount

directionalReturn = direction == BULLISH ? rawReturn : -rawReturn
successCount      = count(directionalReturn > epsilon)
successRatio      = successCount / validOutcomeCount
```

同时返回：`average`、`median`、`minimum`、`maximum`、样本标准差 `stdDev`、线性插值的 `p25/p75`。有效样本为 0 时，这些值全部为 null，比例不返回 0。

样本标准差采用 `n - 1`：

```text
s = sqrt(sum((x_i - mean)^2) / (n - 1))
```

`n = 1` 时 `stdDev = null`。排序与分位数只在单个分组的有效收益数组中完成；P0 单股样本量有硬上限，不存在无界内存增长。

窗口重叠的多个信号仍分别计为独立事件，同时返回 `overlapCount` 和 warning。统计是条件分布描述，不宣称样本相互独立。

## 7. 数据访问与计算流程

### 7.1 数据快照与 READY 判定

`TechnicalSignalReadinessService` 返回：

```ts
export interface TechnicalSignalDataSnapshot {
  ready: boolean
  dataAsOf: string
  dataVersions: {
    tradeCal: string
    stkFactor: string
    daily: string
    adjFactor: string
  }
  missing: string[]
  coverage: {
    expectedOpenDays: number
    factorRows: number
    dailyRows: number
    adjFactorRows: number
  }
}
```

判定顺序：

1. 从 `TushareSyncLog` 成功任务与目标表水位取得 `TRADE_CAL/STK_FACTOR/DAILY/ADJ_FACTOR` 的版本；
2. 最新查询取这些依赖共同完成的最后开市日，而不是直接使用系统日期；
3. 显式历史 as-of 必须不晚于共同水位，并存在交易日历；
4. 对请求股票检查窗口覆盖，但不能因为股票停牌而把市场 dataAsOf 回退到该股最后交易日；
5. 全局同步未完成是接口级 409；单个已到期目标日缺行情是样本级 MISSING；
6. `dataVersions` 使用成功同步日志 ID/完成时间和表水位的稳定组合，参与缓存 key。

现有 `SubscriptionDataReadinessService` 可作为覆盖率和 sync log 校验参考，但应把通用数据集水位能力抽到共享服务，避免技术统计依赖订阅模块。

### 7.2 批量加载

一次请求最多执行固定数量批量查询，不按信号或 occurrence 查询数据库：

1. 股票基本信息与交易所：1 次；
2. 开始日前一条因子：1 次；
3. 窗口内因子所需字段：1 次；
4. 覆盖最大 horizon 的交易日历：1 次；
5. 日线和复权因子：可并行各 1 次；
6. P1 基准日线：1 次。

Prisma 查询必须 `select` 必需字段，按 `(tsCode, tradeDate)` 范围读取。现有主键/索引已满足 P0，不新增索引：

```ts
await prisma.stkFactor.findMany({

  orderBy: { tradeDate: 'asc' },
```

如果改用 `$queryRaw` 聚合 JOIN，只允许 `Prisma.sql` 参数化值和固定白名单表名；严禁拼接 tsCode、日期、signalKey。查询计划必须命中现有复合索引。

### 7.3 事件检测

伪代码：

```ts
const factorPoints = [previousPointBeforeStart, ...pointsInWindow]

for (let i = 1; i < factorPoints.length; i += 1) {
  const previous = factorPoints[i - 1]
  const current = factorPoints[i]
  if (current.tradeDate < windowStart || current.tradeDate > windowEnd) continue

  for (const definition of selectedDefinitions) {
    const evidence = definition.evaluate(previous, current)
    if (!evidence) continue
    occurrences.push(toOccurrence(definition, current.tradeDate, evidence))
  }
}
```

相邻点是相邻的因子记录，不要求自然日连续；但若两个点之间存在本应有行情而因同步缺失造成的 gap，readiness/coverage 检查必须发出 `FACTOR_GAP` warning。窗口第一日能否触发由开始日前一条真实因子决定。

### 7.4 目标日与收益

Repository 把开市日按升序建立 `tradeDate → ordinal` 映射。对信号日在 ordinal `i` 的 occurrence，目标日为 `calendar[i + horizon]`，时间复杂度 O(1)。

```ts
for (const occurrence of occurrences) {
  for (const horizon of horizons) {
    const targetDate = openDates[ordinalByDate.get(occurrence.signalDate)! + horizon]

    if (!targetDate || targetDate > dataAsOf) {
      addImmature(occurrence, horizon, targetDate)
      continue
    }

    const entryDate =
      entryMode === 'SIGNAL_CLOSE' ? occurrence.signalDate : openDates[ordinalByDate.get(occurrence.signalDate)! + 1]

    const outcome = calculateAdjustedReturn(
      quoteByDate.get(entryDate),
      adjustmentByDate.get(entryDate),
      quoteByDate.get(targetDate),
      adjustmentByDate.get(targetDate),
      entryMode,
    )
    addOutcome(occurrence, horizon, outcome)
  }
}
```

复杂度为 O(F + S×E + E×H)，其中 F 是因子行数、S 是信号定义数、E 是事件数、H 是 horizon 数；所有请求参数都有上限。

### 7.5 聚合顺序

必须按以下顺序执行：

1. 解析稳定信号版本；
2. 解析 dataAsOf 与 period 边界；
3. 一次加载最大时间范围；
4. 对最大范围检测 occurrence；
5. 对每个 period 过滤事件；
6. 为事件计算所有 horizon outcome；
7. 按 `period × signalKey × horizon` 对完整样本聚合；
8. 生成摘要；明细接口最后才分页。

禁止“先分页事件、再对当前页求平均”的实现。

### 7.6 Redis 缓存

新增 `src/constant/cache.constant.ts` namespace：`STOCK_TECHNICAL_SIGNAL_STATISTICS`。

```text
key = sha256(
  canonicalRequest
  + dataAsOf
  + sorted(dataVersions)
  + sorted(definitionHashes)
  + statisticsAlgorithmVersion
  + returnPolicyVersion
)
TTL = 24h
```

- canonicalRequest 对 signalKeys、periods、horizons 排序并去重后序列化；
- 数据修正或新同步会产生新 dataVersion，自然旁路旧 key，无需危险的全库 key scan；
- Redis 不可用时 fail-open，直接计算并记录 `cache_unavailable`，不能让核心查询失败；
- 不缓存 4xx/5xx、未 READY、全空或含内部异常的结果；
- 防击穿可使用 5 秒短锁；未拿到锁的请求短暂等待后重查，仍未命中则独立计算；
- 缓存响应前覆盖 `cacheHit` 和 `generatedAt`，不要把用户标识写入共享缓存内容。

## 8. P2 持久化方向

P0 **不修改 Prisma Schema**。只有以下任一条件成立才进入 P2：

- 全市场每日查询量使冷计算长期不能满足 SLO；
- SIGNAL_EVENT 订阅需要全市场 point-in-time 事件；
- 需要跨股票排行或批量研究。

P2 复用关联设计中的模型，至少满足：

```text
TechnicalSignalEvent unique(
  tsCode,
  signalKey,
  semanticsVersion,
  source,
  signalDate
)

TechnicalSignalDailySnapshot unique(
  tradeDate,
  tsCode,
  metricId,
  semanticsVersion
)
```

回填要求：

- 按交易日分片、幂等 upsert、可断点续跑；
- 每批记录 detectorVersion、dataVersion、startedAt/finishedAt、扫描数/命中数/失败数；
- 先 shadow-write，对同一批股票运行在线 detector 与持久化 detector parity；
- 差异必须为 0 才允许查询切读事件表；
- 新版本不得覆盖旧事件，必须并存或显式离线重建；
- 原始行情/因子修复后通过受控回填生成新 dataVersion，不原地制造不可追踪变化。

## 9. 安全、可观测性与运维

### 9.1 安全与资源边界

- 沿用全局 JWT Guard；不得新增公开匿名路由；
- tsCode、日期、signalKey、horizon 全部白名单/格式校验，Repository 不接受自由 SQL 片段；
- 单请求最多 20 个定义、10 个 horizon、10 年窗口、明细 100 条/页；
- evidence 只返回定义声明的指标字段，不序列化完整数据库行；
- 日志不记录 access token、完整请求头或数据库连接信息；
- 对查询超时设置数据库 statement timeout/应用超时，超时返回结构化 503；
- 对昂贵冷查询使用功能级限流和缓存防击穿；
- 统计结果仅为历史描述，API/Swagger 明确非投资建议。

### 9.2 指标

新增低基数 Prometheus 指标：

```text
technical_signal_statistics_requests_total{operation,result,cache_status}
technical_signal_statistics_duration_seconds{operation,cache_status}
technical_signal_outcomes_total{signal_key,horizon,status}
technical_signal_data_gap_total{dataset,reason}
technical_signal_occurrences_total{signal_key,period}
```

禁止把 `tsCode`、userId、requestId、具体日期放进指标 label。`signal_key` 来自有限 Catalog，horizon 只能为 1～60。

结构化日志至少包含：`requestId`、`tsCode`、`dataAsOf`、信号版本、窗口、事件数、有效/缺失/未到期数、缓存状态、各阶段耗时、错误 code。日志里的 tsCode 用于单次排障，不进入高基数时序指标。

### 9.3 告警建议

| 告警       | 条件                             | 处置                                      |
| ---------- | -------------------------------- | ----------------------------------------- |
| API 错误率 | 5 分钟 5xx > 1%                  | 查 DB/Redis/算法异常，必要时关闭功能开关  |
| 冷请求延迟 | 10 分钟 p95 > 1s                 | 查慢查询、连接池、覆盖区间和缓存          |

| 缓存不可用 | 5 分钟 fail-open 持续发生        | 修复 Redis，同时关注 DB 放大流量          |

## 10. 可验证测试方案

### 10.1 测试原则

1. 期望值必须由业务定义和手算 fixture 独立推导，不能读取当前实现结果反推断言；
2. 至少使用三套 oracle：纯函数手算、独立 SQL、API 实际结果；
3. 数值内部比较误差 `< 1e-8`，展示层再检查百分比和舍入；
4. 每个发现的口径缺陷必须增加永久回归用例；
5. 单元测试 mock IO，Repository 集成测试使用真实 PostgreSQL 测试库，不能用 Prisma mock 证明 JOIN 正确；
6. 性能结果记录硬件、数据量、冷/热缓存和运行时间，不能只写“性能正常”。

### 10.2 Golden Fixture

构造开市日：

`20240104, 20240105, 20240108, 20240109, 20240110, 20240111, 20240112, 20240115, 20240116, 20240117, 20240118`。

统计窗口从 `20240105` 开始，`dataAsOf=20240118`。交易日历还需 seed 后续开市日，用于证明最近事件是 IMMATURE。

| 日期  | DIF/DEA          | 原始 close / AF      | 事件与说明                   |
| ----- | ---------------- | -------------------- | ---------------------------- |
| 01-04 | -2 / -1          | 100 / 1              | 窗口外前值，必须用于检测首日 |
| 01-05 | 1 / 0            | 100 / 1              | MACD 金叉                    |
| 01-08 | 2 / 1            | 110 / 1              | 无事件                       |
| 01-09 | 1 / 1            | 90 / 1               | 相等，不触发                 |
| 01-10 | 0 / 1            | 100 / 1              | MACD 死叉                    |
| 01-11 | -2 / -1          | 80 / 1               | 无事件                       |
| 01-12 | -1 / -2          | 80 / 1               | MACD 金叉                    |
| 01-15 | 因子可按场景设置 | 无日线               | 停牌，目标日不得顺延         |
| 01-16 | -2 / -1          | 60 / 2（调整价 120） | MACD 死叉，覆盖复权变化      |
| 01-17 | -1 / -1          | 63 / 2（调整价 126） | 相等，不触发                 |
| 01-18 | 1 / 0            | 63 / 2               | MACD 金叉，无已到期未来收益  |

必须断言：

**金叉共 3 次。**

- T+1：`eligible=2, valid=1, missing=1, immature=1`；唯一有效收益 10%；上涨率 100%；均值/中位数/最小/最大均为 10%；标准差 null。
- T+3：`eligible=2, valid=2, missing=0, immature=1`；收益 `[0%, 57.5%]`；上涨/平盘各 50%；均值和中位数 28.75%；最小 0%；最大 57.5%；样本标准差 40.65864%。

**死叉共 2 次。**

- T+1：收益 `[-20%, 5%]`；上涨/下跌各 50%；均值和中位数 -7.5%；最小 -20%；最大 5%；样本标准差 17.67767%；空头方向性成功率 50%。
- T+3：一个目标日停牌、一个目标日在 dataAsOf 之后；`valid=0`，所有比例、均值、中位数、极值、标准差均为 null。

该 fixture 同时覆盖：窗口边界、相等边界、复权、停牌、截尾、空头方向、零收益和空样本。

### 10.3 单元测试矩阵

| 对象                  | 用例                                               | 关键断言                             |
| --------------------- | -------------------------------------------------- | ------------------------------------ |
| Definition Registry   | 金叉/死叉、相等、连续相等、null、新股首条          | 事件日期与证据严格一致，无重复事件   |
| RSI/BOLL              | 阈值进入、持续状态、离开状态、再次进入             | 只在状态转换日触发                   |
| Period Resolver       | 1Y/3Y、闰年、自定义、上海时区、非开市日            | 边界日期正确，无 UTC 偏移            |
| Calendar Mapper       | 周末、节假日、T+1/T+60、日历尾部                   | 使用市场开市 ordinal，不使用个股行号 |
| Outcome Calculator    | SIGNAL_CLOSE、NEXT_OPEN、除权、价格/AF null 或非正 | 公式与缺失原因正确，无静默降级       |
| Statistics Calculator | 奇偶中位数、0、负数、n=0/1、分位数                 | 分母、n-1 标准差和 null 规则正确     |
| Service Orchestrator  | 多 period/multi-horizon、缓存、超时                | 只批量加载一次，不分页后聚合         |

永久回归用例必须覆盖：

- 百分数被重复乘/除 100；
- 以“个股下一条行情”代替市场 T+1；
- 原始价格在除权日制造假跌；
- 把未到期或缺失收益填 0；
- 用 occurrenceCount 而不是 validOutcomeCount 做比例分母；
- 先过滤窗口再找 previous，导致漏掉窗口首日信号；
- 将连续多日 RSI 超卖重复计为多次事件；
- 摘要只聚合当前明细页。

### 10.4 API 契约测试

使用真实 Nest TestingModule、全局 ValidationPipe/Guard 行为和 Swagger decorator，覆盖：

- 三个端点只接受 POST，响应 DTO 与统一响应包装一致；
- 合法默认请求和全部选项请求；
- 非法 tsCode、日期、跨度、horizon 0/61、重复数组、过长数组、未知 signalKey；
- CUSTOM 字段组合校验；
- 未登录、无权限、限流；
- 股票不存在、数据未 READY、无因子覆盖；
- 明细稳定分页，page 变化不影响 total；
- 错误中不出现 SQL、绝对路径、堆栈或 token；
- 生成的 OpenAPI 中 request/response schema 非空且字段单位明确。

### 10.5 PostgreSQL 集成与独立 SQL 对账

测试数据库 seed `StockBasic/StkFactor/Daily/AdjFactor/TradeCal/TushareSyncLog`，每例使用事务回滚或独立 schema 清理。集成测试覆盖四表日期关联、开始日前置点、停牌、上市期截断、因子 gap、复权 gap 和 sync watermark 不一致。

MACD 独立 SQL oracle 的关键结构如下；先执行 LAG，再过滤窗口：

```sql
WITH factor_with_previous AS (
  SELECT
    trade_date,
    macd_dif,
    macd_dea,
    LAG(macd_dif) OVER (ORDER BY trade_date) AS prev_dif,
    LAG(macd_dea) OVER (ORDER BY trade_date) AS prev_dea
  FROM stock_technical_factors
  WHERE ts_code = $1
    AND trade_date BETWEEN $warmup_date AND $end_date
), events AS (
  SELECT trade_date
  FROM factor_with_previous
  WHERE trade_date BETWEEN $start_date AND $end_date
    AND prev_dif <= prev_dea
    AND macd_dif > macd_dea
)
SELECT trade_date FROM events ORDER BY trade_date;
```

对 Golden Fixture 必须达到“纯函数 oracle = SQL oracle = API”三方完全一致。查询执行 `EXPLAIN (ANALYZE, BUFFERS)`，单股范围查询必须命中 `(ts_code, trade_date)` 主键/索引，不允许全表扫描或按 occurrence N+1。

### 10.6 真实数据抽样对账

从真实库确定性抽样至少 30 只股票，覆盖沪/深/北、主板、创业板、科创板、新股、长期停牌和复权因子变化标的。抽样方式和名单写入执行报告，不随测试重跑随机漂移。

每只股票至少验证：

- 1Y/3Y 的 MACD 金叉/死叉日期；
- T+1/T+5 的预期市场日、有效/缺失/未到期分类；
- 复权收益和涨跌分类；
- 汇总计数恒等式及均值/极值；
- API 的 dataAsOf/dataVersions/definitionHash。

逐事件日期和计数差异必须为 0；浮点绝对误差 `<1e-8`。`000001.SZ` 的既有只读测算可作 smoke baseline，但不能把会随数据修正变化的市场数值写成永久单测。

### 10.7 性能、负载、压力与耐久

基准请求：单股 3 年、8 类信号、5 个 horizon；明细场景另取 100 条。

| 场景         | 验收目标                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------- |
| 单请求冷缓存 | 摘要 p95 < 500ms，p99 < 1s                                                               |
| 单请求热缓存 | 摘要 p95 < 100ms                                                                         |
| LOAD         | 20 VU、10 分钟、至少 100 个标的；p95 < 750ms、p99 < 1.5s、错误率 < 0.1%、吞吐 ≥ 20 req/s |
| STRESS       | 20→50→100 VU；5xx > 5%、CPU 连续 2 分钟 > 85% 或连接池 > 90% 即停止                      |
| SOAK         | 10 VU、60 分钟；末段 p95 相比首段恶化 < 20%，RSS 增长 < 10%，连接数回归基线              |

过载时只允许结构化 429/503，不得进程崩溃；停止压力后 60 秒内恢复。仓库未安装专用压测器时，沿用 Jest + `node:perf_hooks` 编写 `test/fresh/technical-signal-statistics-pressure-v1.spec.ts`，输出 JSON/Markdown 报告，不增加未经评审的生产依赖。

## 13. 风险与缓解

| 风险                        | 等级 | 缓解措施                                                  |
| --------------------------- | ---- | --------------------------------------------------------- |
| 多处信号语义继续分叉        | 高   | Registry 单一事实源；版本/hash；W6 adapter；parity test   |
| 除权导致收益失真            | 高   | Daily × AdjFactor；Golden 除权样本；禁止 fallback 原始价  |
| 停牌导致 T+N 漂移           | 高   | 交易所日历 ordinal；目标日无行情即 MISSING                |
| 缺失/未到期污染均值         | 高   | 明确状态与分母恒等式；null 不转 0                         |
| 分页聚合导致统计偏差        | 高   | 摘要完整计算；明细独立分页；永久回归用例                  |
| 同步部分完成却被当 READY    | 高   | sync log + 表水位 + 覆盖率共同门禁；dataVersions 回显     |
| 算法升级后历史不可复现      | 高   | semantics/statistics/return/data 四类版本；旧版本不可覆盖 |
| Redis 故障放大 DB 压力      | 中   | fail-open、限流、短锁、固定范围查询、告警                 |
| 多 horizon 信号重叠导致误解 | 中   | overlapCount/warning；不声称独立或因果                    |
| 真实可成交性被误解          | 中   | 统计与回测分域；NEXT_OPEN 仅报价口径；免责声明            |
| 全市场扩展后实时计算失控    | 中   | P2 事件物化触发条件、幂等回填和容量门禁                   |
