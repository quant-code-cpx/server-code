## 3. 业务理解

### 3.1 业务场景

用户在研究助手输入“今天佰维存储的表现你来评价一下”。系统应持续展示运行进度，调用所需内部数据 Tool，最终返回可读研究结论。模型某一步已经成功时，审计写入不能反过来让整个研究失败。

### 3.2 核心业务规则

| 编号 | 规则 | 来源 | 测试影响 |
| --- | --- | --- | --- |
| R-001 | 每次用户提交只创建一个可追踪 Run | REST/SSE 契约 | 页面、队列和 DB 的 `runId` 必须一致 |
| R-002 | Run 必须到达 `COMPLETED`、可解释业务失败或用户取消之一 | Agent 终态契约 | 不能因内部审计主键冲突变成通用内部错误 |
| R-003 | 每个逻辑模型调用和调用尝试必须使用不冲突的审计身份 | 审计可追溯性 | 多节点连续调用不能复用同一调用 ID |
| R-004 | 页面通过 POST-SSE 展示进度并在终态刷新消息 | SSE 契约 | 用户不能只看到长时间空白或错误卡片 |
| R-005 | 错误响应不得泄露模型密钥、原始堆栈或他人数据 | 错误码与租户隔离契约 | 页面只显示安全错误；服务端保留 trace/run 证据 |
| R-006 | 同层已有可用事实时，单个行情 Tool 的 `DATA_NOT_FOUND` 应降级为显式 warning | 研究可用性 | 不得丢弃同层已成功的事实包；若同层无替代事实仍须失败 |
| R-007 | 结构化回答必须在模型输出预算内闭合 | 模型网关与 Workflow 契约 | `finish_reason=length` 时压缩修复；当前 Workflow 使用有界回答 schema |

### 3.3 状态变化与不变量

| 类型 | 说明 |
| --- | --- |
| 数据写入 | conversation、message、run、event、model call/attempt、tool call |
| 队列 | `agent-execution` 一个 Run 对应一个幂等 job |
| 权限 | 当前用户只能读取自己的 conversation/run/events |
| 数据不变量 | 同一 Run 的不同模型节点不能发生审计唯一键冲突；终态只能提交一次 |
| 失败策略 | Tool 数据不足应给业务化降级；真实内部异常才映射 `AI_INTERNAL_ERROR` |

## 4. 风险分析

| 风险 | 业务影响 | 测试策略 | 优先级 |
| --- | --- | --- | --- |
| Workflow 多节点复用模型调用 ID | 所有真实研究在 plan 前失败 | 同一 Run 连续执行工具预选和规划 | P0 |
| Worker 正常但 SSE 只得到失败终态 | 页面误以为前端问题 | 对齐页面、SSE、run、worker 日志 | P0 |
| 重试产生重复审计或重复回答 | 数据冲突、用户看到重复结果 | 重试同一失败 Run 与新建 Run | P1 |
| Tool/行情数据不足 | 研究结果不完整 | 验证显式降级而非内部错误 | P1 |
| 结构化回答枚举过多事实 | JSON 被截断，页面等待后失败 | 有界 schema、长度修复、真实 Provider 回归 | P0 |
