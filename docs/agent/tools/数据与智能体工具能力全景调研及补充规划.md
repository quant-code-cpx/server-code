# 数据与智能体工具能力全景调研及补充规划

> 调研基线：2026-08-05 10:12 CST  
> 调研对象：当前工作区代码、运行环境配置、真实 PostgreSQL 数据、Agent 历史会话、Tushare 官方文档  
> 文档性质：现状审计 + 缺口分析 + 可直接实施的 Tool 路线图  
> 分批总路线：[智能体 Tool 分批实施路线后端设计](./智能体工具分批实施路线-后端设计.md)  
> 第一批实施稿：[个股技术与数据可用性 Tool 后端设计](./个股技术与数据可用性工具-后端设计.md)
> 实施更新：五批代码已完成；当前 canonical 为 35（34 只读 + 1 受控写），本地启用 32，未启用可转债与两个联网 Tool。本文原始数据行数仍保留为调研基线。

## 1. 结论

当前问题不是“系统没有数据”，而是“业务数据和计算能力没有完整封装成 Agent Tool”。

- 真实数据库约 42 GB，包含 138 张 public 表、137 个 Prisma Model；A 股行情、技术因子、财务、筹码、两融、股东、事件、指数、基金、期权、转债、宏观等数据已经大量入库。
- 代码中有 17 个 canonical Tool key，其中 16 个只读、1 个写入；当前生产环境只启用 14 个只读 Tool。
- `search_web`、`fetch_web_page`、`save_research_report` 已定义但未启用，联网搜索 Provider 也是 `disabled`。
- 个股技术指标是最明确的 P0 缺口。`stock_technical_factors` 已有 18,218,428 行且更新到 2026-08-04，股票模块也已有技术指标、最新因子、择时信号和 14 类标准信号统计服务，但 Agent 没有对应 Tool。
- “今天特变电工有没有买入信号”失败的直接原因是：Agent 只能查询原始 K 线或全市场前 10 名信号榜，不能按 `600089.SH` 精确读取技术指标/信号。属于 Tool 暴露缺口，不是数据缺失。
- 第一阶段不需要新增上游数据，也不需要先改数据库。应复用现有 Service/Repository，先补精确个股技术 Tool、数据可用性 Tool，并修订选股 Tool 的查询契约；上线前同时补齐 `stk_factor` 全量回补的主动限流和断点恢复。
- 第二阶段再把筹码、两融、事件、股东、相对强弱、指数、基金、行业轮动、因子和宏观能力开放给 Agent。
- 联网新闻与公告属于独立能力：当前本地结构化事件数据可覆盖一部分公司事件，但通用新闻仍需启用受控搜索或新增官方新闻/公告同步链。

建议实施顺序：

1. `get_stock_technical_indicators`
2. `get_stock_technical_signals`
3. `get_data_availability`
4. `screen_stocks@2`
5. 筹码、两融、事件/股东等结构化研究 Tool
6. 指数、基金、行业/因子、宏观 Tool
7. 受控联网、衍生品与高级研究 Tool

## 2. 调研方法与口径

本次没有把旧文档当作当前事实，分别核验了五类证据：

1. Tool 源码：canonical key、Schema、Policy、Facade、Workflow allowlist。
2. 运行配置：实际启用列表、单 Run 调用数、结果大小和数据行数限制。
3. 真实数据库：对关键表执行精确 `COUNT`、`MIN`、`MAX`，并检查数据库规模。
4. 真实失败会话：复盘模型调用了哪些 Tool、收到什么结果、为何仍无法回答。
5. 官方数据源：只用 Tushare 官方接口文档核对接口范围、积分和数据语义。

行数是 2026-08-05 的动态快照，同步任务继续运行后会增加。日期范围中的未来报告期可能来自业绩预告或财务披露计划，不代表未来实际财报已经可得。

这可以完成常规财务质量和成长分析，但还不能覆盖上游财务指标表的完整指标集。扩字段前必须逐项确定单位、累计/单季口径、公告可得时间和空值语义，不能把数据库列直接批量暴露给模型。

## 6. 个股指标失败案例复盘

### 6.1 会话证据

会话 `cmsew0l27000yqdhsua7fnp43` 在 2026-08-05 00:43 收到：

> 今天特变电工有没有买入信号

Agent 依次成功调用：

1. `resolve_security`
2. `get_stock_price_history`
3. `get_stock_overview`
4. `get_stock_moneyflow`

随后回答无法确认，因为返回结果中没有 MACD、KDJ、均线、BOLL、RSI 计算。用户继续问“为什么没有？没提供相关工具吗”，Agent 又调用 `screen_stocks(preset=buy_signal_ranking)`，但该 Tool 只返回全市场排名前 10，只要 `600089.SH` 不在前 10 就仍然无法判断。

### 6.2 数据实际上存在

`stock_technical_factors` 中 `600089.SH` 最新两行真实数据：

| 交易日     |  收盘 | MACD DIF | MACD DEA |  MACD | KDJ K/D/J                |   RSI6 | BOLL 上/中/下            |
| ---------- | ----: | -------: | -------: | ----: | ------------------------ | -----: | ------------------------ |
| 2026-08-04 | 21.38 |   -0.232 |   -0.570 | 0.676 | 76.425 / 68.507 / 92.262 | 68.541 | 21.787 / 20.082 / 18.378 |
| 2026-08-03 | 21.38 |   -0.320 |   -0.655 | 0.670 | 72.971 / 64.547 / 89.819 | 68.541 | 21.660 / 20.044 / 18.427 |

股票业务接口也已实现：

- `detail/analysis/technical`
- `detail/analysis/timing-signals`
- `detail/analysis/factors`
- `detail/analysis/factors/latest`
- `detail/analysis/signal-statistics/query`
- `detail/analysis/signal-occurrences/list`

### 6.3 根因

```text
用户问指定股票技术信号
        │
        ├─ K 线 Tool：只有价格/量/估值，没有技术指标
        │
        ├─ 选股 Tool：只有全市场第一页前 10，没有 tsCode 精确过滤
        │
        └─ 股票模块：已有精确指标和信号服务，但没有注册为 Agent Tool
```

因此根因是“Agent Facade/Tool 缺失 + Tool 路由语义不完整”。不能通过提示词要求模型自己算 MACD 来解决；那会增加公式差异、复权差异、序列截断和幻觉风险。

另有一次“说一下今天特变电工的表现”失败是模型结构化输出超长，没有进入 Tool 调用。这属于模型输出可靠性问题，应与数据/Tool 覆盖缺口分别治理。

## 9. P0 Tool 契约建议

### 9.1 `get_stock_technical_indicators`

职责：返回程序已计算的指标事实，不负责解释“买入/卖出”。

建议输入：

```json
{
  "tsCode": "600089.SH",
  "asOfDate": "2026-08-05",
  "lookback": 2,
  "indicators": ["MACD", "KDJ", "RSI", "BOLL"],
  "includeSeries": true
}
```

约束：

- `lookback` 1–500，默认 2。
- `indicators` v1 只允许数据库已验证有值的 `MACD`、`KDJ`、`RSI`、`BOLL`，最多 4 类。
- `asOfDate` 解析为不晚于该日的最近 READY 交易日；盘中不能把未收盘日期描述成完整日线。
- v1 只读取 `StkFactor`，不在同一版本内回退到另一计算来源；需要 MA/EMA/WR/DMI/SAR 时发布新版本并明确来源。
- `StkFactor` 中 `cci_14`、`cci_20`、`tr`、`atr14`、`atr20`、`vr_26` 全表实测均为空，CCI/ATR/VR 在完成字段契约修复、回补和质量验收前不得加入 Tool enum。

建议输出核心字段：

```json
{
  "tsCode": "600089.SH",
  "requestedAsOf": "2026-08-05",
  "dataThrough": "2026-08-04",
  "adjustment": "FORWARD_SNAPSHOT",
  "calculationSource": "TUSHARE_STK_FACTOR",
  "items": [],
  "qualityFlags": ["LATEST_COMPLETED_TRADE_DAY_USED"]
}
```

### 9.2 `get_stock_technical_signals`

职责：返回版本化、可审计的信号判断，区分“状态”和“当日触发事件”。

建议输入：

```json
{
  "tsCode": "600089.SH",
  "asOfDate": "2026-08-05",
  "sections": ["CURRENT", "OCCURRENCES", "STATISTICS"],
  "signalKeys": ["macd.golden-cross", "kdj.golden-cross", "rsi6.oversold-enter"],
  "lookbackDays": 60,
  "horizons": [1, 3, 5, 10, 20],
  "includeBenchmark": false
}
```

建议输出每个信号必须包含：

- `signalKey`、`semanticsVersion`。
- `kind=EVENT|STATE`，避免把“MACD 位于零轴下”当成金叉事件。
- `side=BUY|SELL|WARNING|NEUTRAL`。
- `triggeredOnDataThrough`。
- 触发证据，如前后两日 DIF/DEA、K/D、RSI 阈值。
- 数据截止日、复权口径、样本成熟度、缺失原因。
- 统计 section 才返回样本数、前瞻收益、MFE/MAE、置信区间和基准超额。

现有 14 个标准定义可以直接作为 v1 catalog：MACD/KDJ 金叉死叉、RSI6 超卖/超买进入、BOLL 上破/下破、均线多头/空头排列进入、SAR 多空状态进入、20 日量比放大/缩小进入。

### 9.3 `get_data_availability`

职责：回答“系统有没有这类数据、最新到哪天、为何查不到”，降低模型误判。

建议输入可以是 `datasets` 或 `tsCode + capabilities`，输出：

- `status=READY|DEGRADED|BLOCKED|EMPTY|UNKNOWN`。
- `coverageStart`、`dataThrough`、`lastSyncedAt`。
- `sourceTask`、`sourceModels`。
- `rowCountScope`，说明是全表、证券还是请求窗口。
- `qualityFlags`，如短历史、公告修订缺失、数据源延迟、空表。
- `recommendedTool`，帮助 Planner 选择正确 Tool。

该 Tool 只读同步水位和数据质量，不开放管理员同步命令。

### 9.4 `screen_stocks@2`

建议变更：

- 增加 `tsCodes`，最多 20 个，用于验证指定股票是否满足同一套筛选条件。
- 增加 `page` 或稳定 `cursor`；`pageSize` 可提高到 50，但仍受结果字节限制。
- 返回 `matchedFilters`、`matchedSignals` 和关键原始值，不能只给总分。
- 保留全市场 `buy_signal_ranking` 单次调用约束，避免模型分批取榜后错误合并。
- Planner 明确路由：指定股票信号用技术信号 Tool；全市场筛选/排名才用 `screen_stocks`。

## 10. 落地架构

### 10.1 代码边界

建议复用现有 NestJS 领域服务，新增面向 Agent 的有界 Facade：

```text
Agent Tool Definition
        │ JSON Schema + Policy + 审计
        ▼
Domain Tool Facade
        │ 单位、时点、质量、行数、错误标准化
        ▼
现有 Service / Repository / Prisma
```

建议文件落点：

- `src/apps/agent/tools/adapters/technical-analysis-tools.ts`
- `src/apps/agent/tools/adapters/data-availability-tools.ts`
- `src/apps/stock/stock-technical-tool.facade.ts`
- `src/apps/technical-signal/technical-signal-tool.facade.ts`
- `src/apps/agent/data-availability/data-availability.facade.ts`

需要同步更新：

- `src/apps/agent/contracts/tool-keys.ts`
- `src/config/agent-tools.config.ts`
- `src/apps/agent/agent.module.ts`
- Workflow v4 Tool allowlist、Planner 路由提示和能力映射
- Tool Registry/Policy/Executor 契约测试
- 模型工具调用、真实 PostgreSQL、Run/SSE 端到端测试

不要让 Agent 直接注入 `PrismaService`，不要复用 Controller，也不要新增 `query_database`、任意 SQL、任意 HTTP 或任意代码执行 Tool。

### 10.2 公共输出元数据

新增 Tool 都应继续使用统一 `ToolResult`，至少包含：

- `requestedAsOf`
- `asOf` / `dataThrough`
- `coverageStart`
- `sourceModels` / `sourceServices`
- `unit` / `currency` / `adjustment`
- `dataVersion` / `algorithmVersion` / `semanticsVersion`
- `warnings` / `qualityFlags`
- `truncated` / `nextCursor`
- `auditId`

技术指标尤其要区分三种来源：Tushare 社区预计算指标、本地确定性引擎、模型解释。前两者可以成为引用事实，模型解释不能反向伪装成指标源。

### 10.3 Tool 数量控制

不建议“一张表一个 Tool”。优先按用户意图组织：

- 同一对象、同一权限、同一数据量级的能力，用 `sections` 合并。
- 语义明显不同或成本差异大的能力拆开，例如原始技术指标与历史信号统计。
- 私有数据、公共数据、确定性计算、联网研究分别注册 Policy。
- 每次新增 Tool 都补 Planner 路由样例和反例，避免模型只看名称猜调用方式。

## 11. 数据源与联网能力判断

### 11.1 P0 不需要新增 Tushare 权限

现有库存已经覆盖 P0：

- [股票技术因子 `stk_factor`](https://tushare.pro/document/2?doc_id=296)：官方说明覆盖全历史、单次最多 10,000 条；5000 积分每分钟 100 次，8000 积分以上每分钟 500 次；指标基于前复权价格。
- [每日筹码及胜率 `cyq_perf`](https://tushare.pro/document/2?doc_id=293)：官方说明从 2018 年开始、单次最多 6,000 条、5000 积分。
- [每日筹码分布 `cyq_chips`](https://tushare.pro/document/2?doc_id=294)：官方说明从 2018 年开始、单次最多 6,000 条、5000 积分。
- [融资融券明细 `margin_detail`](https://tushare.pro/document/2?doc_id=59)：现有同步链和数据库已经在使用。
- [财务指标 `fina_indicator`](https://tushare.pro/document/2?doc_id=79) 和 [业绩预告 `forecast`](https://tushare.pro/document/2?doc_id=45)：现有数据库已有数据，后续主要是 Tool 语义和字段治理。

`stk_factor`、`cyq_perf`、`cyq_chips` 是 Tushare 社区计算数据，回参必须标记来源和算法/复权语义，不能描述为交易所原始披露。

P0 Agent Tool 只读本地 PostgreSQL，因此每次用户查询不会调用 Tushare，也不会消耗接口频次。频控风险只在同步链：日常增量通常 1 个开放交易日、约 5,500 行，单次请求即可完成；从 1990 年开始的 full 回补可能产生约 8,500 次请求。当前 `TushareClient` 对 `stk_factor` 尚无主动间隔，只能在 `40203` 后等待重试，所以上线前必须增加默认 650 ms 的可配置间隔、逐日成功断点、失败即停和恢复测试。精确改造见[实施稿第 9 节](./个股技术与数据可用性工具-后端设计.md#9-stk_factor-同步限流加固)。

### 11.2 新闻与公告需要独立决策

当前有两条路径：

1. 启用已有 Brave 受控搜索和网页抓取，适合快速补通用新闻；继续沿用签名 URL、SSRF 防护、引用和审计。
2. 新增官方结构化公告/新闻同步，适合可重复研究和定时任务；需要单独评估接口权限、版权、保留期和更新频率。

Tushare 官方目录已经包含新闻、上市公司公告等语料接口，但部分接口不是普通积分权限。以 [新闻通讯接口说明](https://tushare.pro/document/2?doc_id=195) 和 [接口权限说明](https://tushare.pro/document/1?doc_id=108) 为准，不能假设现有 Token 自动可用。

建议短期先启用受控搜索；中期只同步高价值结构化公告，不把任意网页抓取结果直接写入业务事实表。

## 12. 测试与验收门禁

### 12.1 P0 业务黑盒用例

| 用例                                 | 期望                                                                                                |
| ------------------------------------ | --------------------------------------------------------------------------------------------------- |
| “今天特变电工有没有买入信号”         | 解析为 `600089.SH`；使用最近 READY 交易日；调用精确技术信号 Tool；返回明确是/否、信号语义和原始证据 |
| “特变电工最新 MACD、KDJ、RSI 是多少” | 返回 `dataThrough`、指标值、复权口径；不得回答“没有工具”                                            |
| 盘前问“今天”                         | 明确最新完整数据是上一交易日，不把盘中日期当收盘数据                                                |
| “全市场买入信号最多的股票”           | 只调用一次 `screen_stocks` 排名，不逐股循环                                                         |
| 指定股票不在全市场前 10              | 仍能用精确 Tool 返回结果，不把“未进榜”解释为“无信号”                                                |
| 请求首版不支持的 CCI/ATR/VR          | Schema 返回 `INVALID_ARGUMENT`；不补造数字，也不静默切换到另一来源                                  |
| 查询新闻且搜索禁用                   | 返回明确 typed capability error，不假装已联网                                                       |

### 12.2 工程门禁

- JSON Schema：非法证券代码、日期、指标和超限数组均拒绝。
- Policy：公共市场数据、用户私有数据、计算和写操作权限分离。
- 真实数据库：至少验证有数据、无数据、短历史、截止日落后、空字段五类场景。
- 点时性：财务和事件按公告可得时间，不只看报告期。
- 算法：技术信号和后续收益使用固定版本、固定复权、固定入场价语义。
- 结果大小：序列截断必须有 `truncated/nextCursor`，不能静默裁剪。
- 性能：P0 单股快照 P95 目标小于 300 ms，500 日序列 P95 目标小于 1 s；信号统计单股三年 P95 目标小于 2 s。
- 回归：现有 17 个 Tool key、工作流、SSE 和审计事件不能破坏。

## 14. 最终建议

可以直接进入实现，不需要再做一轮纯方案讨论。建议先完成 P0 四项，其中两个技术 Tool 是最高优先级；它们能直接修复已经发生的用户失败，而且完全复用现有数据与代码。

不建议先扩大模型权限、让模型自行计算技术指标或开放通用 SQL。这些做法无法解决数据时点、复权、单位、审计和信号语义问题，反而会降低研究结果可信度。

各批的逐字段 Schema、Facade/Module 边界、Workflow 版本、逐文件修改清单、测试矩阵、灰度和回滚步骤，以[智能体 Tool 分批实施路线后端设计](./智能体工具分批实施路线-后端设计.md)及其链接的五份批次设计为实施依据。
